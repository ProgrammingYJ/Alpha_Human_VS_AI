## 이전 PC A/B 병렬 엔진과 웹 계약 (2026-11-05 이력)

11/05 사용자의 A/B 실제 병렬 추론 요청으로 당시 단일 FIFO 운영 기본값을 대체했다. 이 단락과 뒤 측정값은11/05 이력이며11/06 단일 구역·30% 시간 예산이 현재 운영 기본값이다. 원격 실행기 하나가 존재·사람·나무 가중치 한 벌을 공유하며 `SharedModels(..., execution_mode="parallel")`의 독립 작업 슬롯2개와 CUDA stream2개를 사용한다. A/B는 각자 슬롯을 확보해 사진 준비·카운트다운·출발 뒤 추론을 진행하므로 한 레인이 다른 레인의 준비/추론 완료를 기다리는 단일 큐를 사용하지 않는다. 각 방의 인간/AI 공통 출발은 유지하며 서로 다른 방의 절대 출발 시각을 강제로 맞추지 않는다.

각 작업은 `fork_for_inference()`(`fork_for_worker()` 별칭)로 만든 predictor 문맥을 사용한다. 두 제한 모델과 나무 모델의 가중치는 동일 객체이고, 나무 processor/tokenizer·`last_detections`와 메타데이터는 작업별로 분리한다. fork는 모델의 eval·장치 준비 상태를 확인하고 병렬 예측 중 `model.to()`·`eval()`을 반복하지 않는다. 작업 스레드는 자기 CUDA stream과 `torch.inference_mode()` 안에서 실행하고 자기 stream 완료만 동기화한 뒤 결과를 반환한다. 합성 RGB 예열은 방 연결 전에 두 문맥 모두 수행한다.

11/05 당시 기본 실행은 `Start-Alpha-Remote.cmd`였으며 당시 명시적 직렬 복구는 `Start-Alpha-Remote.cmd -InferenceMode serial`, Python 직접 실행은 `--inference-mode parallel|serial`이다. `serial`은1슬롯 FIFO로 복구하며 실행기를 레인마다 두 개 켜지 않는다. 시작/라운드 보고서의 `inference_mode`, `max_concurrent_inferences`, `cuda_stream_count`, `model_weights_shared`로 실제 설정을 확인한다. 50:50 하드웨어 할당이나 모든 주제의 속도 향상·통신/화면 지연0을 보장하지 않는다. 최신 CUDA 출력/시간/VRAM 검증과 운영 프로세스는 STATUS가 정본이다.

프로토콜3·각 방의 세 역할9사진 준비·출발 전 문제 추론 금지·같은 방 다음 참가자·500ms 전달 여유/250ms 선택 계획은 유지한다. 취소·만료·오류는 해당 슬롯과 라운드에 한정하고 다른 레인의 작업을 해제하거나 중단하지 않는다. 가중치·전처리·임계값·학교 미사용·임의 오답 금지와40%/ONNX/Pi/legacy OS 입력 미완료도 유지한다.

11/05 실제 운영 `SharedModels`를 고정 공개 RGB 두 묶음으로 검사했다. 4유형의16개 순서 있는 조건쌍을 serial/parallel 각각3회 실행했으며 선택 번호·보고 예측의 최대 차이는0, 공유 가중치 객체 동일, OOM0이었다. 두 작업 전체 소요의 중앙값(serial→parallel)은 사람+사람0.534→0.376초, 나무+나무3.504→2.948초였지만 나무+사람은1.553→2.206초로 느려졌다. 모든 조합이 빨라진다는 근거로 쓰지 않는다. 최대 PyTorch 할당1522.18MiB·예약3226MiB는 이 표본의 관측값이다.

나무+나무 별도 Kineto 추적에서44,969개 CUDA kernel·두 stream17/21과 서로 다른 stream의 실제 kernel 겹침0.553852초를 확인했다(GPU 활성 구간 합집합2.857961초). 호스트 호출 겹침을 넘어 GPU 실행이 실제 겹친 이 사례의 근거이며50:50 자원 분할·행사장 무지연 보장은 아니다. 원본은 `runs/parallel-operating-20261105/cuda-report.json`이다. 이 저장 RGB 검사는 HTTP/브라우저·정확도·장시간 부하 검증과 별개이며 공개 두 방 검사·최신 운영 재시작/PID는 STATUS를 따른다.

## 명확한 사진과 활성 문제은행 교체 (2026-11-02)

작은 사람·가려진 건물·가는 맨가지·원경 수관·경계가 불분명한 물 장면을 보수적으로 제외한다. 나무 총수를 모르는 숲은 `treeCount=null`과 명확한 `treeAtLeast3`를 유지하고 모르는 라벨을 채우지 않는다. 새 사진은 원문 이용 조건·저자·촬영일·원본 SHA와 촬영 그룹을 확인하며 같은 원본/연속 촬영을 한 격자에 반복하지 않는다. 이번 AI 시각 재검토는 독립 사람 검수나 정확도 시험이 아니다.

직전 속도 정책(2026-10-27): 사용자 요청으로 연속 AI 타일 선택의 최소 간격을 기존1초에서 **0.25초(250ms)**로 변경한다. remote의 PC 대기와 서버 수락 조건, legacy PC/Pi 클릭 정책에 같은 하한을 적용한다. 계획 없는 진행 중 remote AI 표시만125ms 폴링하고 계획 수신 후·인간 화면·대기/결과 등은500ms를 유지한다. 한 참가자당 한 판이다. remote 인간의 시작 요청은 먼저 GPU 예약 대기로 들어가고 타이머는0초다. PC 준비가 돌아오면 인간이 다시 시작한다. 자동으로 다음 경기를 시작하지 않으며 새 방/새 코드는 초기 설정·복구에만 필요하다. legacy는 기존 한 방 한 판/새 코드 절차를 유지한다. 90초 시간초과는 미확정 운영 가안이며 네트워크0ms나 정확한 동시 렌더링을 보장하지 않는다.

`POST /api/rooms/{id}/next`는 human만 현재 종료 `roundId`로 요청한다. 결과를 lobby로 전환하되 방/코드/토큰을 보존하고 다음 start에서 새 roundId·사진·정답·시각을 만든다. 봇 표시 화면은 결과 후 **다음 참가자 대기 · 연결 유지**로 남으며 다시 코드를 입력하지 않는다. UI는 room revision·roundNumber·단계·선택 sequence와 서버 시각으로 지난 응답을 거부하고, 이전 round의 늦은 사진 로딩 콜백도 무시한다. 이전 참가자의 선택/오답 안내가 다음 참가자 화면에 남지 않도록 초기화한다.

10/27 A/B별 인간/AI 표시 역할의 개발을 승인받아 remote를 기본으로 구현했고 후속 요청으로 화면을 컴퓨터 브라우저에서 운영한다. A/B는 독립 방이며 한 방 종료가 다른 방을 종료시키지 않는다. 인간은 오답 후 수정할 수 있고, PC 봇은 고정 예측을 한 번 제출한 뒤 결과를 기다린다. AI 표시 화면은 타일·준비·제출을 조작하지 못한다. PC가 HTTPS로 고정 예측을 한 번 보내면 서버 일정으로 최소0.25초 간격의 선택과 한 번 제출을 처리하고 AI 표시 화면은 이를 서버시계로 보간한다. 구형 서버의 개별 선택 전송은 호환 경로로 남는다. 이는 화면에 실제 마우스/터치 입력 주입이 아니다.

새 remote 시작은 AI 표시 화면 등록·프로토콜3 PC 엔진의 준비·15초 이내 heartbeat를 확인한다. 구형 PC 실행기는 업데이트/재시작 전 새 시작을 허용하지 않는다. 표시 화면의 `viewerConnected`는 참가 등록 여부이며 사진 로드나 현재 화면 생존의 증명이 아니다. loading에서 실제9장 디코딩 준비를 별도로 확인한다. 구역과 역할별 세션을 분리하고 기대 구역과 다른 코드는 거절한다. 사람 응답에는 AI 선택 집합을 보내지 않는다. 사진은 양쪽 모두 `object-fit: contain`으로 전체가 보인다.


## GPU 예약 후 출발 (10/27 사용자 승인)

기본 remote의 인간 시작 요청은 `{expectedRevision}`을 보내 먼저 `queued`에 들어간다. 이때 `startRequest={id,requestedAt,expiresAt}`를 표시하고 회차는 그대로이며 `roundId/startAt/deadlineAt/topic=null`, `tiles=[]`다. 화면은 타이머0·선택/제출 불가·AI 출발 준비를 표시한다. PC가 GPU 차례를 확보하면 새 round를 loading으로 만들고 사진을 미리 준비한다. 세 역할의 준비 후 공통 카운트다운을 확정하며 실제 출발 후에만 보관한 RGB를 추론한다. 현재 single은 한 경기이며 모델 호출/자원 대기를 마치고 GPU를 해제한 뒤 실제 예측의 선택 계획을 보낸다. 네트워크·화면 지연0을 보장하지 않는다.

인간은 `cancel-start {requestId}`로 GPU 대기·사진 준비·출발 전 카운트다운을 취소하고 같은 방에서 다시 시작할 수 있다. 수동 취소·PC 연결 만료·PC 오류·GPU 대기120초/사진 준비60초 만료의 서버 사유를 구분한다. 제한 시간은 운영 가안이다. revision/요청ID/사진 epoch로 오래된 응답을 거부하며 다음 참가자도 동일 방/코드를 유지한다. UI는 `gpuReservationSupported=true`와 `imageBarrierSupported=true`인 프로토콜3 PC만 새 출발을 허용하고 구형 실행기는 업데이트를 안내한다. 이전 비배리어 진행 라운드 완료와 legacy의 기존 시작은 유지한다.

출발 전 자기 슬롯을 확보하고 각 방의 사진 준비를 지키며 사전 정답 추론·사후 시간 보정·임의 오답은 없다. 모델/전처리/임계값·학교 사용·최소0.25초 선택은 유지한다. UI 회차/비밀필드/오류20개·TypeScript·대상 ESLint를 통과했고 서버/Python 통합·실제 GPU/브라우저·최종 배포/가동 결과는 STATUS를 따른다. 기존 대기/추론 기록에는 active 상태 조회 HTTP도 포함되므로 순수 GPU 시간으로 해석하지 않는다.


## 고정 ML 선택 계획 API

`POST /api/rooms/{id}/engine`의 `action:"plan"`은 engine만 `{roundId,selectedIndices:[0..8]}`로 요청한다. 중복 없는0~9개 타일을 순서 그대로 보존하며 실제 정답 개수를 채우지 않는다. 새 계획은 playing·현재 round·15초 이내 준비된 엔진·아직 선택/제출하지 않은 상태에서만 CAS로 수락한다. 응답은 `{plan:{roundId,selectedIndices,startAt,intervalMs:250,submitAt},serverNow}`이고 상태/정답/라벨은 포함하지 않는다. 같은 순서의 재전송은 결과 뒤에도 동일 일정으로 ACK하며 변경 계획은 `plan_conflict`로 거부한다. 계획이 있는 판의 개별 선택/제출은 `plan_active`다. 종료 시각 이전에 끝낼 수 없는 계획은 `plan_too_late`로 거부한다.

정답 여부는 서버만 계산해 round에 비공개로 저장한다. 조회 또는 인간 제출이 예정 제출을 정산하며, 인간 채점 트랜잭션과 SQL 자체가 이미 도래한 완벽한 봇 제출보다 늦은 인간 승리를 막는다. 같은 밀리초 경계에서는 예정 봇 제출이 우선한다. 도래 전 인간이 먼저 완벽하게 제출하면 인간이 이기고 나머지 재생은 중단한다. 오답 계획은 한 번의 제출 시각/오답만 기록하고 인간의 수정/재제출을 막지 않는다. 시간초과 경계의 봇 승리는 금지하며 다음 참가자의 새 round는 계획 없이 시작한다. 인간 응답에는 계획과 미래 선택을 제공하지 않는다. 이 서버 재생은 실제 PC 모델이 이미 낸 결과를 실행하는 결정적 어댑터다.

Node의 `server/selection-plan.test.mjs`는 경계·CAS·단일 승자·privacy·구형 입력과의 경합·다음 회차를 검증한다. `server/selection-plan.http.test.mjs`는 숨긴 관리자 키를 사용하는 localhost 전용 서버 채점 검사이며 실제 ML 엔진과 분리한다. 여기의 기대 정답은 이 테스트 프로세스에만 존재하고 모델/봇에 제공하지 않는다. 배포·실제 PC 및 브라우저 검증·사진 등록 결과는 STATUS를 따른다.

## 사진 준비

관리 화면에서 JPEG·PNG·WebP 사진을 선택한 뒤 사람 수, 정확한 나무 수 또는 3그루 이상 여부, 건물/연못 존재, 원본 그룹, 출처를 검토해 등록한다. 모르면 미확인으로 남긴다. 숲의 정확한 총수를 모를 때 나무 수를 3으로 지어내지 않는다. 각 조건의 모든 정답 수를 지원하려면 사람/건물/연못은 최소4양성7음성, 나무는4양성6음성의 독립 원본 그룹이 필요하다. 데이터가 부족하면 시작을 거부한다.

정답과 원본 메타데이터는 서버 D1에만 저장한다. R2 사진은 라운드별 임의 ID로 전달한다. remote loading/countdown에는 현재 round의 준비용 다운로드를 허용하고 화면은 숨긴다. legacy는 시작 전 접근을 막으며 공통으로 만료/이전 라운드 접근을 차단한다. no-store와 원본 RGB를 유지한다. 학교 사진과 로컬 Kaggle 데모34장은 공개하지 않는다. 10/27까지의 공개 Commons46장/12,362,595bytes는 이전 은행 이력이며 이번34장 교체의 실제 운영 활성 수·등록/검증 결과는 STATUS가 정본이다. 사진·정답은행은 웹 소스나 빌드 자산에 넣지 않고 D1/R2에서 제공한다.

## PC 원격 엔진 실행 — 기본 운영

이 웹화면은 모델을 자동 실행하지 않는다. 프로젝트 루트의 **Start-Alpha-Remote.cmd**를 PC에서 한 번 실행하면 존재·사람·나무 모델을 CUDA에 불러오고 single/.30/CPU4 지속 운영 콘솔을 연다. 인간 기본 주소에서 방 하나를 만들고 AI 표시 화면을 연결한 뒤 PC 콘솔에 같은8자리 코드만 한 번 입력한다(`A CODE8` 호환). 입력은 숨겨지며 코드·토큰을 결과 파일에 남기지 않는다. 다음 참가자는 인간의 **다음 참가자 준비 → PC 준비 확인 → 대결 시작하기 → GPU 예약 대기/사진 준비 → 공통 출발**을 반복한다. 대기는 취소 후 같은 방에서 재시도할 수 있다. PC worker는 같은 engine 연결/heartbeat를 유지하며 매 경기 새 RGB에 고정 모델로 한 번 예측한다. 새 방은 초기 설정·복구에만 만든다. 가중치1벌·worker1·CUDA stream1과 기존 배치의 호출별30% 시간 예산을 사용한다. 실제 모드·예산·CPU 적용은 startup 보고서로 확인하며 최신 가동·반복 검증은 상위 STATUS를 따른다.

`scripts/run_remote_engine.py`의 별도 `engine` 역할은 heartbeat·선택·제출을 담당하고, 웹 `bot` 역할은 읽기 전용 표시를 담당한다. 이 remote 경로는 사용자가 승인한 HTTPS 행동 경로다. OS 마우스·브라우저 자동화·F8 좌표 보정을 사용하지 않는다. Python CLI 자체는 dry-run이 기본이며 `--execute`가 있어야 방에 참가하고, 운영용 cmd는 이를 명시해 실행한다. 기록은 `runs/remote-engine/`의 새 실행 폴더에 남는다.

엔진은 loading 때 공개 타일 URL을 사진 바이트 전송에만 사용해9장 RGB를 보관한다. 실제 공통 출발 뒤 공개 질문과 같은9장 RGB를 모델에 전달하며 경기 중 사진 재다운로드를 하지 않는다. 파일명·URL/ID·서버 라벨·실제 정답수·정답 파일을 ML 입력이나 판정 근거로 사용하지 않는다. 사람은 SSDLite, 건물/연못은 MobileNetV3 Small v1, 나무 수는 고정 Grounding DINO Tiny다. 추가 학습·학교 튜닝·임계값 변경은 없으며 네 조건의40%는 미달성이다. 선택0개도 모델 결과 그대로 한 번 제출한다. 가짜 선택이나 상위k개 강제 선택을 넣지 않는다.

인간이 먼저 정답을 내거나 진행 중 round가 종료/변경되면 해당 경기의 남은 선택·제출을 취소한다. 서버는 engine 권한·방/라운드·선택 순서·중복·최소0.25초 간격·첫 승자를 검사한다. AI 표시 토큰으로 ready·next·선택·제출할 수 없다. 현재 내부 A의 방·역할 토큰·라운드 기록을 구분한다. 이전 단발 CUDA 두 방 연결은 `runs/remote-booth-local-v2/verification.json`에서 passed=true로 확인했다.
