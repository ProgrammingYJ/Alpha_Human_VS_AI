- 한 문제에 서로 다른 원본 그룹의 사진 9장을 넣는다. 모델은 상위 4개 강제 선택이나 정답 파일 조회를 하지 않는다.

한 참가자당 한 판이다. remote 인간의 시작 요청은 먼저 GPU 예약 대기로 들어가고 타이머는0초다. PC가 차례를 확보하면 새 round의 사진9장을 먼저 준비한다. 세 역할이 준비된 뒤 서버가 약2초 뒤 공통 출발 시각을 기록하고 양쪽은 보관한 사진을 공개한다. legacy는 기존 시작을 유지한다. 정답 타일 집합과 완전히 일치하는 제출을 먼저 서버가 수락하면 즉시 승리를 확정하고 그 경기를 닫는다. 인간은 오답이면 타이머를 유지하며 수정·재제출할 수 있다. 동시 정답 요청도 D1 트랜잭션으로 승자 한 명만 확정한다. 양쪽 화면은 같은 서버 종료 시각으로 멈춘다. 계획 없는 진행 중 remote AI 표시만125ms, 계획 수신 뒤와 인간 화면/그 외 단계는500ms 폴링하며 진행 중 요청은 겹쳐 보내지 않는다. remote에서는 인간이 **다음 참가자 준비**를 눌러 같은 방·코드·레인·역할 연결을 유지하고 선택·사진 로딩·타이머를 비운다. PC 준비가 돌아오면 인간이 다시 시작한다. 자동으로 다음 경기를 시작하지 않으며 새 방/새 코드는 초기 설정·복구에만 필요하다. legacy는 기존 한 방 한 판/새 코드 절차를 유지한다. 90초 시간초과는 미확정 운영 가안이며 네트워크0ms나 정확한 동시 렌더링을 보장하지 않는다.

`POST /api/rooms/{id}/next`는 human만 현재 종료 `roundId`로 요청한다. 결과를 lobby로 전환하되 방/코드/토큰을 보존하고 다음 start에서 새 roundId·사진·정답·시각을 만든다. 봇 표시 화면은 결과 후 **다음 참가자 대기 · 연결 유지**로 남으며 다시 코드를 입력하지 않는다. UI는 room revision·roundNumber·단계·선택 sequence와 서버 시각으로 지난 응답을 거부하고, 이전 round의 늦은 사진 로딩 콜백도 무시한다. 이전 참가자의 선택/오답 안내가 다음 참가자 화면에 남지 않도록 초기화한다.

10/27 A/B별 인간/AI 표시 역할의 개발을 승인받아 remote를 기본으로 구현했고 후속 요청으로 화면을 컴퓨터 브라우저에서 운영한다. A/B는 독립 방이며 한 방 종료가 다른 방을 종료시키지 않는다. 인간은 오답 후 수정할 수 있고, PC 봇은 고정 예측을 한 번 제출한 뒤 결과를 기다린다. AI 표시 화면은 타일·준비·제출을 조작하지 못한다. PC가 HTTPS로 고정 예측을 한 번 보내면 서버 일정으로 최소0.25초 간격의 선택과 한 번 제출을 처리하고 AI 표시 화면은 이를 서버시계로 보간한다. 구형 서버의 개별 선택 전송은 호환 경로로 남는다. 이는 화면에 실제 마우스/터치 입력 주입이 아니다.

새 remote 시작은 AI 표시 화면 등록·프로토콜3 PC 엔진의 준비·15초 이내 heartbeat를 확인한다. 구형 PC 실행기는 업데이트/재시작 전 새 시작을 허용하지 않는다. 표시 화면의 `viewerConnected`는 참가 등록 여부이며 사진 로드나 현재 화면 생존의 증명이 아니다. loading에서 실제9장 디코딩 준비를 별도로 확인한다. 구역과 역할별 세션을 분리하고 기대 구역과 다른 코드는 거절한다. 사람 응답에는 AI 선택 집합을 보내지 않는다. 사진은 양쪽 모두 `object-fit: contain`으로 전체가 보인다.


## GPU 예약 후 출발 (10/27 사용자 승인)

기본 remote의 인간 시작 요청은 `{expectedRevision}`을 보내 먼저 `queued`에 들어간다. 이때 `startRequest={id,requestedAt,expiresAt}`를 표시하고 회차는 그대로이며 `roundId/startAt/deadlineAt/topic=null`, `tiles=[]`다. 화면은 타이머0·선택/제출 불가·AI 출발 준비를 표시한다. PC가 GPU 차례를 확보하면 새 round를 loading으로 만들고 사진을 미리 준비한다. 세 역할의 준비 후 공통 카운트다운을 확정하며 실제 출발 후에만 보관한 RGB를 추론한다. GPU를 해제한 뒤 A/B 선택은 독립 진행한다. 두 방의 절대 출발 시각이나 전체 반응시간이 같아진다는 보장은 아니다.

인간은 `cancel-start {requestId}`로 GPU 대기·사진 준비·출발 전 카운트다운을 취소하고 같은 방에서 다시 시작할 수 있다. 수동 취소·PC 연결 만료·PC 오류·GPU 대기120초/사진 준비60초 만료의 서버 사유를 구분한다. 제한 시간은 운영 가안이다. revision/요청ID/사진 epoch로 오래된 응답을 거부하며 다음 참가자도 동일 방/코드를 유지한다. UI는 `gpuReservationSupported=true`와 `imageBarrierSupported=true`인 프로토콜3 PC만 새 출발을 허용하고 구형 실행기는 업데이트를 안내한다. 이전 비배리어 진행 라운드 완료와 legacy의 기존 시작은 유지한다.

예약으로 경기 중 GPU 경합 대기를 타이머 시작 전으로 옮기며 사전 정답 추론·사후 시간 보정·임의 오답은 없다. 모델/전처리/임계값·학교 사용·최소0.25초 선택은 유지한다. UI 회차/비밀필드/오류20개·TypeScript·대상 ESLint를 통과했고 서버/Python 통합·실제 GPU/브라우저·최종 배포/가동 결과는 STATUS를 따른다. 기존 대기/추론 기록에는 active 상태 조회 HTTP도 포함되므로 순수 GPU 시간으로 해석하지 않는다.


## 고정 ML 선택 계획 API

`POST /api/rooms/{id}/engine`의 `action:"plan"`은 engine만 `{roundId,selectedIndices:[0..8]}`로 요청한다. 중복 없는0~9개 타일을 순서 그대로 보존하며 실제 정답 개수를 채우지 않는다. 새 계획은 playing·현재 round·15초 이내 준비된 엔진·아직 선택/제출하지 않은 상태에서만 CAS로 수락한다. 응답은 `{plan:{roundId,selectedIndices,startAt,intervalMs:250,submitAt},serverNow}`이고 상태/정답/라벨은 포함하지 않는다. 같은 순서의 재전송은 결과 뒤에도 동일 일정으로 ACK하며 변경 계획은 `plan_conflict`로 거부한다. 계획이 있는 판의 개별 선택/제출은 `plan_active`다. 종료 시각 이전에 끝낼 수 없는 계획은 `plan_too_late`로 거부한다.

정답 여부는 서버만 계산해 round에 비공개로 저장한다. 조회 또는 인간 제출이 예정 제출을 정산하며, 인간 채점 트랜잭션과 SQL 자체가 이미 도래한 완벽한 봇 제출보다 늦은 인간 승리를 막는다. 같은 밀리초 경계에서는 예정 봇 제출이 우선한다. 도래 전 인간이 먼저 완벽하게 제출하면 인간이 이기고 나머지 재생은 중단한다. 오답 계획은 한 번의 제출 시각/오답만 기록하고 인간의 수정/재제출을 막지 않는다. 시간초과 경계의 봇 승리는 금지하며 다음 참가자의 새 round는 계획 없이 시작한다. 인간 응답에는 계획과 미래 선택을 제공하지 않는다. 이 서버 재생은 실제 PC 모델이 이미 낸 결과를 실행하는 결정적 어댑터다.

Node의 `server/selection-plan.test.mjs`는 경계·CAS·단일 승자·privacy·구형 입력과의 경합·다음 회차를 검증한다. `server/selection-plan.http.test.mjs`는 숨긴 관리자 키를 사용하는 localhost 전용 서버 채점 검사이며 실제 ML 엔진과 분리한다. 여기의 기대 정답은 이 테스트 프로세스에만 존재하고 모델/봇에 제공하지 않는다. 배포·실제 PC 및 브라우저 검증·사진 등록 결과는 STATUS를 따른다.

## 사진 준비

관리 화면에서 JPEG·PNG·WebP 사진을 선택한 뒤 사람 수, 정확한 나무 수 또는 3그루 이상 여부, 건물/연못 존재, 원본 그룹, 출처를 검토해 등록한다. 모르면 미확인으로 남긴다. 숲의 정확한 총수를 모를 때 나무 수를 3으로 지어내지 않는다. 각 조건의 모든 정답 수를 지원하려면 사람/건물/연못은 최소4양성7음성, 나무는4양성6음성의 독립 원본 그룹이 필요하다. 데이터가 부족하면 시작을 거부한다.

정답과 원본 메타데이터는 서버 D1에만 저장한다. R2 사진은 라운드별 임의 ID로 전달한다. remote loading/countdown에는 현재 round의 준비용 다운로드를 허용하고 화면은 숨긴다. legacy는 시작 전 접근을 막으며 공통으로 만료/이전 라운드 접근을 차단한다. no-store와 원본 RGB를 유지한다. 학교 사진과 로컬 Kaggle 데모34장은 공개하지 않는다. 10/27까지의 공개 Commons46장/12,362,595bytes는 이전 은행 이력이며 이번34장 교체의 실제 운영 활성 수·등록/검증 결과는 STATUS가 정본이다. 사진·정답은행은 웹 소스나 빌드 자산에 넣지 않고 D1/R2에서 제공한다.

루트 scripts/import_public_booth_bank.py는 명시적으로 공개승인된 비학교 CC0/PD 은행만 받는다. 기본 dry-run이며 실제 등록은 --execute --admin-key-stdin과 메모리의 관리자 키를 사용한다. 기존 local Kaggle importer의 공개업로드 금지는 유지한다. 출처는 비공개 provenance로 보존하며 알려지지 않은 라벨을 정답 개수에 맞춰 만들지 않는다.

## PC 원격 엔진 실행 — 기본 운영

이 웹화면은 모델을 자동 실행하지 않는다. 프로젝트 루트의 **Start-Alpha-Remote.cmd**를 PC에서 실행하면 존재·사람·나무 모델을 CUDA에 한 번 불러오고 지속 운영 콘솔을 연다. 초기 A/B 방을 만들고 같은 구역의 AI 표시 화면을 연결한 뒤, PC 콘솔에 `A CODE8` 또는 `B CODE8` 형식으로 코드를 한 번 입력한다. CODE8은 실제8자리코드 자리다. 입력은 숨겨지며 코드·토큰을 결과 파일에 남기지 않는다. 다음 참가자는 인간 화면의 **다음 참가자 준비 → PC 준비 확인 → 대결 시작하기 → GPU 예약 대기 → 공통 출발**을 반복한다. 대기는 취소 후 같은 방에서 재시도할 수 있다. PC worker는 같은 engine 연결/heartbeat를 유지하며 매 경기 새 RGB에 고정 모델로 한 번 예측한다. 새 방은 초기 설정·복구에만 만든다. 모델은 재사용하고 GPU 추론은 잠금으로 직렬화하므로 A/B 추론 대기가 같다고 보장하지 않는다. 최신 재사용 지원 엔진의 실제 가동·반복 검증은 상위 STATUS를 따른다.

`scripts/run_remote_engine.py`의 별도 `engine` 역할은 heartbeat·선택·제출을 담당하고, 웹 `bot` 역할은 읽기 전용 표시를 담당한다. 이 remote 경로는 사용자가 승인한 HTTPS 행동 경로다. OS 마우스·브라우저 자동화·F8 좌표 보정을 사용하지 않는다. Python CLI 자체는 dry-run이 기본이며 `--execute`가 있어야 방에 참가하고, 운영용 cmd는 이를 명시해 실행한다. 기록은 `runs/remote-engine/`의 새 실행 폴더에 남는다.
