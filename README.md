네 유형 중 하나와 독립 사진9장을 추첨해 양쪽에 같은 배열을 제공합니다. 인간 시작 요청 뒤 GPU 차례를 기다린 다음 사진9장을 미리 준비합니다. 인간 화면·AI 표시 화면의 사진 디코딩과 PC의RGB 수신이 모두 끝나야 약2초 공통 카운트다운으로 출발합니다. 준비 중 사진과 질문은 숨겨 두고 타이머는0입니다. 출발 때 이미 받은 사진을 그대로 표시하며 PC도 보관한RGB로 추론합니다. 예약 대기에는 문제/사진이 공개되지 않고 타이머0이며 대기를 취소할 수 있습니다. **한 참가자당 한 판이며 먼저 모든 정답을 고르고 오답을 제외해 제출한 쪽이 승리하면 즉시 종료됩니다.** 오답이면 같은 문제·시작 시각으로 수정·재제출할 수 있습니다. 다음 참가자는 같은 방에서 준비 버튼으로 초기화한 뒤 다시 시작하며 봇 연결 코드는 유지합니다. 기본90초 제한은 미확정 운영 가안입니다.

사진 관리에서 사람 수, 나무 정확 수 또는3그루 이상 여부, 건물·연못, 원본 그룹·출처·사용 메모를 확인해 올립니다. 모르는 값은 미확인으로 둡니다. 원본·연속촬영·크롭은 같은 그룹으로 기록합니다. 모든 정답 수를 지원하려면 사람/건물/연못 각각 최소4양성7음성, 나무4양성6음성의 독립 그룹이 필요합니다. 부족하면 시작하지 않습니다. 정답은 서버에만 있으며 모델에 실제 정답 수·라벨·원본 파일명을 전달하지 않습니다.

## 모델과 실제 확인 범위

사람 수는 **SSDLite320 MobileNetV3 Large**, 건물·연못은 **MobileNetV3 Small**의 기존 제한 학습 v1을 사용합니다. 두 모델은 검토된 Kaggle train17장/41장으로 각각1epoch만 추가 학습했고 대규모 COCO/ImageNet 사전학습을 이미 거쳤습니다. **YOLO는 사용하지 않았습니다.** 나무3그루 이상은 존재 점수로 셀 수 없어 별도 공식 사전학습 **Grounding DINO Tiny**를 고정해 연결했습니다. 나무 모델의 프로젝트 추가 학습은 없습니다.

실제 CUDA에서 저장 RGB 시연4문제를 실행했습니다. 건물 문제는 선택 집합이 맞았고 사람 수·나무 수·연못은 틀렸습니다. 재사용 시연 사진의 기능 검사이며 일반 정확도25%나 목표40% 달성의 근거가 아닙니다. 조건별 선택·시간·한계는 STATUS에 기록했습니다. v1과 나무 임계값을 이 실패에 맞춰 재튜닝하지 않았습니다.

화면 RGB→ML→좌표→최소0.25초 간격 타일 클릭·제출 경로는 코드로 구현했습니다. **ML 봇의 실제 OS 화면 캡처·타일 클릭·제출은 아직 미검증**입니다. 이전 URL 확인 실패 이후 이번에는 Chrome 확장으로 사진9장과 타이머가 실제 표시되는 것을 확인했습니다. 사진 표시 검사에서는 답안 선택·제출을 하지 않았습니다. 기본 설정은 `calibrated=false`이며 좌표는 실측 전입니다. 현재 봇은 한 판에 고정 ML 선택을 한 번 제출하고 오답 자동 재시도는 없습니다. 상대가 이기면 남은 입력을 취소합니다.

기존 4정답·5오답 평가에서 유형별 약40%라는 개발 목표는 아직 달성하지 못했습니다. 기존8조건과 현재 웹4종·가변 정답 수의 성능을 섞지 않습니다. 충분한 새 Kaggle train/선택val/미사용audit를 먼저 정해야 합니다. **학교 사진은 이번 행사에서 사용하지 않습니다.** 학교 촬영·문제 등록·학교 최종 평가를 현재 계획에서 제외합니다. 미래 학교 자료의 개발 학습/튜닝 차단은 유지합니다. ONNX 출력 동등성·Pi 기기/추론/GUI 입력도 남아 있습니다.

## 컴퓨터 브라우저 A/B 운영

11/02에 GPU 2스트림 동시 추론을 별도 실험했습니다. 고정 사진 9장씩 두 작업의 각 3회 중앙값은 존재+사람 0.386→0.299초로 줄었지만 나무+존재 1.171→1.847초, 나무+나무 2.238→3.033초로 늘었습니다. 출력은 일치하고 메모리 부족은 없었습니다. **운영은 기존 FIFO를 유지하며 동시 추론은 아직 적용하지 않았습니다.** GPU를 50%씩 보장해 나누거나 모든 조합의 지연이 줄었다는 결과가 아닙니다. 측정 범위·메모리·공식 출처는 [STATUS](docs/STATUS.md)를 따릅니다.

11/07(토) 행사 전 이번 배포의 자체 검증 결과를 STATUS에서 확인하고 운영 기기에서 다시 시험합니다. 사진 준비 대기와250ms 선택 간격은 의도된 절차이며 인터넷/브라우저의 모든 지연이0이 된다는 뜻은 아닙니다.

최신 요청으로 인간과 AI 표시 모두 **컴퓨터 브라우저**에서 운영합니다. 기존 Android4대 계획을 대체하며 컴퓨터/모니터 대수는 아직 정하지 않았습니다. Chrome에서 인간 화면과 AI 표시 화면을 각각 열면 됩니다. 모델은 기존 RTX PC에서 실행하고 다른 컴퓨터에는 Python/ML 설치가 필요 없습니다. 행사 기기의 실제 화면·마우스 선택/제출·시작/종료·네트워크 리허설은 별도로 확인합니다.

현재 부스 기본 입력은 원격 모드입니다. **AI 계산은 이 PC에서 하고, AI 표시 브라우저는 모델이 선택한 타일을 표시합니다.** 인간은 직접 마우스로 답안을 고릅니다. AI 선택은 서버 이벤트이므로 같은 PC에서도 참가자의 마우스를 빼앗지 않습니다. 각 방에서 PC 엔진과 표시 브라우저를 별도 권한으로 연결합니다.

| 화면 | 접속 주소 |
|---|---|
| 인간 A | https://human.marulee.dev/?lane=A |
| 봇 표시 A | https://bot.marulee.dev/?lane=A |
| 인간 B | https://human.marulee.dev/?lane=B |
| 봇 표시 B | https://bot.marulee.dev/?lane=B |

1. 운영 컴퓨터와 인터넷을 켜고 모델 실행 PC의 전원·절전 상태를 확인합니다. Chrome에서 필요한 A인간/A봇/B인간/B봇 화면을 엽니다. 같은 PC의 별도 창/모니터 또는 다른 컴퓨터에 배치할 수 있습니다. 동시에 볼 화면은 탭 전환 대신 별도 창/모니터에 배치합니다.
2. PC에서 [Start-Alpha-Remote.cmd](Start-Alpha-Remote.cmd)를 한 번 실행하고 세 모델 로드 후 `레인과 새 연결 코드 (입력 숨김)>`를 기다립니다. 이미 켜 둔 실행기는 중복 실행하지 않습니다.
3. 최초에만 인간 A 화면에서 방을 만들고 코드를 AI 표시 A 화면에 입력합니다. 모델 PC 콘솔에도 `A 코드8자리`를 입력한 뒤 Enter를 누릅니다. A 뒤 공백과 실제8자리코드이며 입력 글자가 보이지 않는 것이 정상입니다. B도 같은 방식으로 연결합니다.
4. 각 인간 화면에서 PC 준비와 AI 표시 연결을 확인한 뒤 참가자가 시작을 요청합니다. GPU 대기→사진 준비 화면에서 인간/AI 표시/PC의9장 준비를 기다립니다. 두 브라우저는 사진9장을 실제 디코딩하고 PC는 최대3개 병렬로RGB를 받습니다. 모두 준비된 뒤 약2초 공통 출발하며 인간은 타일 선택/정답 제출, AI는 보관한RGB의ML 판별→고정 선택 목록 한 번 전송을 수행합니다. 준비 중 한쪽이 느리거나 사진 수신에 실패하면 먼저 출발시키지 않습니다. 서버는 접수 후0.5초 표시 여유를 두고250ms 간격으로 재생해 마지막 선택 시 한 번 제출합니다. AI 화면은 계획을 받으면50ms 시계로 표시하고 상태는500ms 조회합니다(계획 없는 구형 진행 중 화면만125ms). 통신/브라우저 지연으로 정확한250ms 표시를 보장하지는 않습니다.
5. 한 참가자는 한 판입니다. 종료 후 인간 화면의 **다음 참가자 준비**를 누르면 같은 방·코드·연결을 유지하며 선택·타이머·결과를 초기화합니다. 다음 사람이 **대결 시작하기**를 누르면 새 문제로 진행합니다. AI 표시 화면과 PC에는 코드를 다시 입력하지 않습니다. A/B의 진행은 독립이며 모델도 다시 로드하지 않습니다.
6. 기존 OS 실행기는 legacy입니다. 원격 운영에는 F8 좌표 보정과 PC 브라우저 전면 유지가 필요하지 않습니다. 원격 봇의0개 선택/오답 제출은 실제 모델 결과일 수 있으며 엔진 미실행과 구분합니다.
7. 마감 시 PC 콘솔에 `quit`을 입력하고 Enter를 누릅니다. 연결한 구역을 잘못 지정했다면 `stop A` 또는 `stop B`로 해당 PC 작업을 멈출 수 있습니다. 이미 서버가 수락한 선택 계획은 계속 실행됩니다. 운영자는 서버의 경기 상태를 확인한 뒤 연결을 복구합니다.

모델 PC와 각 브라우저는 인터넷 연결이 필요합니다. AI 표시 화면은 자기 사진 준비만 알리며 타일 수정·엔진 준비·답안 제출 권한은 없습니다. 엔진 생존 알림은3초 주기이고 서버는15초가 지나면 연결이 끊긴 것으로 표시합니다. 최초 엔진 참가 뒤 첫 알림 전에는 ‘연결 확인 중’이며, 새 알림을 읽은 뒤의 서버 시각으로 실제 생존을 판단합니다. 대기 중에도 연결을 유지합니다. 표시 연결 등록과 사진 준비는 별도입니다. 출발에는 해당 화면의9장 디코딩 확인이 필요하며 출발 전 페이지를 다시 열면 준비를 다시 확인합니다. 출발 후 새로고침은 이미 시작한 경기를 정지하지 않습니다.

통신은 각 브라우저·모델 PC가 Cloudflare 서버에 보내는 **HTTPS API 요청과 폴링**입니다. PC끼리 전용 TCP 소켓을 직접 연결하는 구조는 아닙니다. 현재 Python 봇과 같은 urllib 경로의 읽기 전용 요청에서 HTTP/1.1(TLS/TCP)을 확인했고 브라우저의 실제 HTTP버전은 미측정입니다. 모델은 실행기 하나에 한 번 올려 공유하며 A/B는 독립적으로 진행하고 GPU 추론만 차례로 처리합니다. 따라서 실행기를 두 개 켜지 말고 한 콘솔에 A와 B를 연결합니다. 기존 공개 두 세션 검사는 통과했으나 겹친 추론의 대기와 행사 장시간 운용은 구분합니다.

**A 참가자가 푸는 동안 B도 경기를 진행할 수 있습니다.** A의 모델 추론이 끝나면 GPU를 해제해 A의 선택 표시·인간 풀이와 B의 준비/추론을 겹칩니다. 두 레인이 시작을 동시에 요청하면 B는 경기 시작 전에 기다릴 수 있고 A/B의 절대 출발 시각은 달라집니다. 각 방 안의 인간과 AI는 그 방의 사진 준비가 끝난 뒤 함께 출발합니다. 공개 검사에서 B의 예약 전 대기는10.438초였고 경기 중 GPU 대기는 두 방 모두0초였습니다. 예약 전 값에는 다른 방의 준비·카운트다운과 상태 HTTP도 포함되므로 순수 GPU 계산시간으로 보지 않습니다. 이는 현재 PC의 두 세션 처리 근거이며 모든 유형 조합·현장 네트워크·장시간 운용의 지연0 보장은 아닙니다.

**시작 요청→GPU 예약 대기→양쪽 화면/PC 사진 준비→공통 출발→추론 후 GPU 해제**를 구현했습니다. 한 실행기의 FIFO 예약 대기를 경기 타이머 전에 처리하고, 이미 분석한 방의250ms 서버 선택 계획과 다음 방의 준비/추론을 겹칠 수 있습니다. 대기 취소·연결 만료·오류는 대기실로 돌아갑니다. GPU 대기120초 상한은 운영 가안입니다. 새 출발에는 사진 준비를 지원하는 프로토콜3 PC 실행기가 필요합니다. 이번 업데이트 재시작 후에는 새 방으로 한 번 연결하고 이후 참가자 교체는 같은 방을 유지합니다. 사전 문제 풀이·사후 시간 보정은 하지 않습니다. 네트워크/질문별 모든 지연을 같게 보장하는 것은 아닙니다.

현재 모델은 각 라운드마다 예측을 한 번 하고 그 선택 목록만 서버에 한 번 보냅니다. 서버가 이미 수락한 계획은 PC가 끊겨도 완료하며, 인간이 먼저 맞히면 종료 시각에서 남은 선택을 중단합니다. 미래 선택 목록은 AI 표시 화면에만 제공하고 사람에게 정답/모델 계획을 미리 주지 않습니다. 0개로 예측하면 가짜 클릭 없이0개로 제출하며 오답 안내를 표시합니다. 같은 라운드의 자동 재추론은 없고 다음 참가자의 새 라운드에는 새 사진을 추론합니다. 모델과 임계값을 이번 연결 결과에 맞춰 바꾸지 않았습니다.

실제 CUDA 두 방에서 선택/제출과 HTTP 표시 상태 일치를 확인했고, 별도 브라우저 경기에서도 실제 모델의 선택 체크를 확인했습니다. 이는 연결 검사이며 목표40% 또는 학교 사진 정확도 검증이 아닙니다. 최신 연결 상태 검사와 게시 버전은 [STATUS](docs/STATUS.md)를 따릅니다. 행사장의 실제 컴퓨터 배치·네트워크 리허설은 남아 있습니다.
