## GPU 예약과 사진 준비 후 출발

기본 remote의 인간 시작 요청은 `{expectedRevision}`을 보내 먼저 `queued`에 들어간다. 이때 `startRequest={id,requestedAt,expiresAt}`를 표시하고 회차는 그대로이며 `roundId/startAt/deadlineAt/topic=null`, `tiles=[]`다. PC가 GPU 차례를 확보한 뒤 `begin`으로 새 round를 `loading`에 만들고 인간/AI 표시의 숨긴9장 디코딩과 PC9장 RGB 준비를 기다린다. 같은 준비 epoch의 세 ACK 뒤에만 공통2초 카운트다운을 확정하며 준비 대기에는 시간0·문제/사진 비공개를 유지한다. 출발 때 같은 이미지/RGB를 재사용하고 모델 추론을 시작하며 반환 후 GPU를 해제한 뒤 A/B 선택은 독립 진행한다. 두 방의 절대 출발 시각이나 모든 네트워크/렌더링 지연이 같아진다는 보장은 아니다. 실제 적용 버전/검사는 STATUS를 따른다.

인간은 `cancel-start {requestId}`로 출발 대기를 취소하고 같은 방에서 다시 시작할 수 있다. 수동 취소·PC 연결 만료·PC 오류·대기 만료의 서버 사유를 구분한다. 대기 제한120초와 사진 준비60초는 운영 가안이다. 새 queued/취소/재요청의 revision과 요청ID를 비교해 오래된 상태·실패 알림이 새 요청을 덮지 못하며, 다음 참가자도 동일 방/코드를 유지한다. 새 출발은 `gpuReservationSupported=true`·`imageBarrierSupported=true`인 protocol3 PC 실행기와 준비 계약을 요구한다. 구형 실행기는 업데이트/재시작을 안내하며 이미 진행하던 구형 라운드 완료·legacy의 기존 시작과 구분한다.

예약으로 경기 중 GPU 경합 대기를 타이머 시작 전으로 옮기며 사전 정답 추론·사후 시간 보정·임의 오답은 없다. 모델/전처리/임계값·학교 사용·최소0.25초 선택은 유지한다. UI 회차/비밀필드/오류20개·TypeScript·대상 ESLint를 통과했고 서버/Python 통합·실제 GPU/브라우저·최종 배포/가동 결과는 STATUS를 따른다. 기존 대기/추론 기록에는 active 상태 조회 HTTP도 포함되므로 순수 GPU 시간으로 해석하지 않는다.
