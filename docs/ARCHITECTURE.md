## 이전 A/B 병렬 추론 운영 구조 (2026-11-05 이력)

11/05 사용자의 A/B 실제 병렬 추론 요청으로 당시 단일 FIFO 운영 기본값을 대체했다. 이 단락과 뒤 측정값은11/05 이력이며11/06 단일 구역·30% 시간 예산이 현재 운영 기본값이다. 원격 실행기 하나가 존재·사람·나무 가중치 한 벌을 공유하며 `SharedModels(..., execution_mode="parallel")`의 독립 작업 슬롯2개와 CUDA stream2개를 사용한다. A/B는 각자 슬롯을 확보해 사진 준비·카운트다운·출발 뒤 추론을 진행하므로 한 레인이 다른 레인의 준비/추론 완료를 기다리는 단일 큐를 사용하지 않는다. 각 방의 인간/AI 공통 출발은 유지하며 서로 다른 방의 절대 출발 시각을 강제로 맞추지 않는다.

각 작업은 `fork_for_inference()`(`fork_for_worker()` 별칭)로 만든 predictor 문맥을 사용한다. 두 제한 모델과 나무 모델의 가중치는 동일 객체이고, 나무 processor/tokenizer·`last_detections`와 메타데이터는 작업별로 분리한다. fork는 모델의 eval·장치 준비 상태를 확인하고 병렬 예측 중 `model.to()`·`eval()`을 반복하지 않는다. 작업 스레드는 자기 CUDA stream과 `torch.inference_mode()` 안에서 실행하고 자기 stream 완료만 동기화한 뒤 결과를 반환한다. 합성 RGB 예열은 방 연결 전에 두 문맥 모두 수행한다.

사진 준비60초·GPU 대기120초·경기90초는 운영 가안이다. 준비 실패·취소·만료는 대기실로 복귀하고 인간이 다시 시작한다. 기존15초 엔진 생존 검사는 유지한다. 단순 viewer 참가나 모델 로드만으로 사진 로딩 완료를 표시하지 않는다. 새 서버에는 protocol3가 필요하고 과거 v11처럼 사진 준비 지원 필드가 없는 서버만 protocol2로 협상한다. 새 서버가 지원false를 알리는 경우는 준비 전 상태이므로 배리어를 우회하지 않는다. 대기실에서 새 서버 배포를 관측하면 같은 엔진 토큰으로 다음 생존 알림을3으로 올리며 이미 진행 중인 구형 판은 기존 계약으로 끝낸다.

PC는 방 연결을 허용하기 전에 합성 회색 RGB9장으로 존재·사람·나무 세 고정 모델을 예열한다. 실제 문제·학교 사진·정답은 예열에 사용하지 않고 startup에 모델 로드/예열/전체 시간을 나눠 기록한다. 건물·연못에는 기존 존재 모델만, 사람 문제에는 기존 사람 검출 모델만 실행해 질문과 무관한 연산을 생략한다. 가중치·전처리·임계값·NMS·계수·타일 선택 규칙은 유지하며 미실행 항목은 None으로 남긴다. 전체 예측 API는 보존하고 같은 공개 RGB9장에서 전체 실행과 대상별 점수/계수·선택 동등성을 별도 검사한다.

Python 기본 통신은 origin에 묶인 표준 http.client의 HTTP/1.1 연결을 호출 스레드별로 재사용한다. 리다이렉트·관리 API·외부 호스트는 허용하지 않으며 엔진 토큰은 방 API에만 전달한다. 읽기 GET은 일시 연결 오류에 한 번만 재시도한다. begin·사진 준비·불변 plan·개별 sequence는 기존 멱등 본문을 그대로 제한 재전송하며 일반 POST를 무조건 재전송하지 않는다. 새 배리어+plan 경로의 추론/선택 stage 표시는 주기 heartbeat로 전송해 경기 안의 동기 왕복을 줄인다. GPU 예약/사진 준비의 서버 확인과 모델 직전 상태 확인, 서버의 계획/승패 검증은 유지한다. 사진3개 worker와 연결은 종료 시 정리한다.

사진 준비에는 추가 migration `0004_amazing_namora.sql`이 round의 준비 번호/만료 시각/세 역할 준비 플래그5열을 더한다. 기존0000~0003은 변경하거나 다시 적용하지 않는다. 실제 로컬/운영 적용은 STATUS를 확인한다.

검증 스크립트 `scripts/verify_continuous_booth.py`는 실제 PC 모델을 한 번 로드해 A두판+B한판을 진행하고, 인간/봇 역할도 각각9개 공개 RGB를 실제 다운로드·PIL 디코딩한 뒤 준비를 알린다. A첫판 인간 준비를3초 보류해 PC/봇 준비 뒤에도 타이머0·사전 추론0인지 검사한다. 이 보류는 시험 조건이며 운영 지연 설정이 아니다. HTTP/PIL 시험은 실제 브라우저 렌더링 시험과 별개다. 같은 RGB의 출력 동등성과 준비/모델/HTTP 시간, 경기 중 사진 다운로드0을 기록하며 독립 정확도·목표40% 달성이나 지연0을 주장하지 않는다. 실제 게시/실측·현장 기기/네트워크의 미확인 범위는 STATUS가 정본이다.


## 목표와 현재 상태
송내고등학교 알파 동아리의 자체 CAPTCHA에서 AI가 사진을 판별하고 타일을 클릭한다. 학습은 Windows PC의 RTX 4070 Laptop GPU, 실행 목표는 PC와 Raspberry Pi 4B다. **10/26 사용자의 새 요청으로 사람·봇 웹사이트와 서버 대결도 현재 프로젝트 범위에 포함했다.** 이전의 참가자 사이트 별도 경계는 이번 요청 범위에서 대체한다.

10/22에는 RTX 4070 Laptop GPU에서 존재 판별기와 사람 검출기를 각각 1 epoch 제한 학습하고 저장 3×3 RGB → 예측 → 조건 판정 → 좌표 dry-run을 연결했다. 10/26에는 웹/API·로컬 데모·봇 실행기와 별도 사전학습 나무 계수 후보를 추가했다. 앞선 게시 검증에서는 네이티브 Chrome URL 확인 실패로 화면 시험을 중단했고 다른 입력 도구로 우회하지 않았다. 이번 공개 사진 요청에서는 Chrome 확장 연결로 배포된 인간 화면을 확인했다. 이 브라우저 점검과 **ML 봇의 실제 OS 캡처·클릭·제출 검증**은 별개이며, 후자는 아직 미완료다. ## 확정된 문제와 경기 규칙
- 현재 웹은 네 유형 중 하나를 뽑고 등록 사진 은행에서 매번 9장을 구성한다. 이전 고정 5문제 구상과 현재 서버 구현을 구분한다.
- 고정 3×3, 타일 9개에 서로 다른 독립 사진을 사용한다. 한 사진을 9조각으로 자르는 방식이 아니다.
- 현재 웹 질문은 `person_count gte 3`, `tree_count gte 3`, `building_present`, `pond_present`다. 사람 n=2~5의 일반 ML 조건과 `eq`/`gte` 판정은 기존 Python 기능으로 보존한다.
- 정답률은 학습량·모델 성능을 제한해 **유형별 약 40%의 전체 선택 집합 성공률**을 목표로 한다. `configs/calibration-target-v2.json`은 목표와 평가 경계만 고정하며 달성 모델이 아니다. 수치 허용오차와 목표 인간 승률은 미정이다. v1 프로필·체크포인트·이미 공개한 test는 보존하고 재튜닝하지 않는다.
- 정답 4칸은 이번 평가 기준이다. 실제 부스의 모든 문제를 4정답으로 확정한 것은 아니며, 풀이기에 정답 수를 알려주거나 상위 4개를 강제 선택하지 않는다.
- 현재 웹 정답 수는 사람/건물/연못 2~4칸, 나무 3~4칸이다. 이 범위는 서버 출제 정책이며 봇의 선택 개수를 강제하는 입력이 아니다.
- 최신 경기 규칙은 **한 참가자 한 라운드**다. 먼저 완벽한 정답 집합을 제출한 쪽이 즉시 승리하고 양쪽 모두 종료한다. 사람은 오답을 수정해 다시 제출한다.10/27 후속 승인으로 remote는 같은 방·코드·역할 토큰을 유지하며 결과의 ‘다음 참가자 준비’ 뒤 사람이 새 라운드를 시작한다. 자동 연속 시작은 아니다. 기존 OS/legacy만 한 방 한 판·새 참가자 새 방을 유지한다.
- PC와 Pi 모두 연속된 타일 클릭 사이를 **최소0.25초**로 제한한다. 추론 주기나 문제당 처리 주기의 제한이 아니다. 첫 클릭과 제출 시점은 별도 계약이다.

기존 대표 장면 하나를 고르는 단일 분류 계획은 이 대상 존재·사람 수 과제로 대체한다. 나무·건물·사람이 같은 사진에 함께 있을 수 있으므로 이를 하나의 상호배타적 softmax 클래스로 합치지 않는다.

## 전체 구성과 남은 구현
```text
구현: Kaggle 검토 manifest → 그룹 분할 → 제한 GPU 학습 → PyTorch 두 체크포인트
구현: 저장 3×3 격자 RGB → 독립 타일 9개 → 대상별 점수 + 사람 검출/계수
                      → 공개 조건 판정 → 선택 타일 → 좌표·예정 시각 dry-run
남음: ONNX 내보내기·출력 비교 → Pi 추론 → 화면 캡처·실제 OS 클릭·사이트 연동
준비: 새 Kaggle 그룹/라벨 → 선택용 val 격자 → 제한 v2 후보 비교 → 모델 고정 → 새 audit 1회
```

웹과 봇의 경로는 다음과 같이 분리한다.

```text
운영자 등록 → 서버 전용 사진 메타데이터/정답(D1) + 원본 바이트(R2)
                    → 역할 대기실 → 같은 서버 startAt → 같은 공개 9타일
사람 화면 클릭 ──────────────────────────────────────→ 서버 exact-set 채점
봇 화면 RGB + 공개 조건 → 실제 ML → 좌표 → 0.25초 타일 클릭 → 화면 제출 → 서버 채점
원격 방 공개9사진 RGB(최대3병렬/원순서) + 공개 조건 → PC 공유 ML → 선택계획1회 업로드
                                                              → 서버500ms 여유/250ms 재생·최종제출 → 서버 채점
                                                         └→ 해당 봇 브라우저의 읽기 전용 선택 표시
```

봇 풀이 경로는 정답 은행·관리자 API·원본 파일명·사진 ID별 정답을 읽지 않는다. 로컬 데모 준비/관리자 업로드와 특권 서버 채점 테스트는 봇 실행기와 별도 도구다.

v1은 나무·건물·연못의 다중 라벨 판별기와 사람 검출기를 나눈 구조다. 존재 판별기는 MobileNetV3 Small의 features와 BN 통계를 고정하고 classifier만 학습했다. 사람 검출기는 COCO 사전학습 SSDLite의 backbone과 BN 통계를 고정하고 검출 head를 학습했다. 두 모델 모두 학습 전후 고정 영역의 state hash가 같음을 확인했다. 사람 존재는 유효 검출 수 1 이상으로 파생하며 MobileNet 분류 점수로 인원 수를 지어내지 않는다.

사람 수는 class 1 검출에 고정 score 0.5·NMS IoU 0.45를 적용한 뒤 원본 높이 8픽셀·면적 64픽셀 이상인 유효 상자로 계산한다. 일부 보임·가림·작은 사람·군중의 검토 기준과 검출 학습 가능 여부를 분리한다. 사람 있음/없음 이진 라벨만으로 인원 계수를 학습하지 않았으며, 밀집 군중·매우 작은 사람은 한계다.

존재 판별용 검토본은 70장(train 41 / val 14 / test 15)이다. 사람 검출 자료는 검토되고 완전 bbox 사용이 허용된 train 17장 / val 3장 / test 18장으로 나눴으며 최적화에는 train만 사용했다. 미확정 인원 수·군중·미주석은 계속 unknown/crowd/null로 남기며 검토되지 않은 box 개수를 정답으로 자동 승격하지 않는다. 검토는 작은 Kaggle 표본에 대한 것이며 학교나 전체 사진 분포를 대표하지 않는다.

개발용 `review_labels.py`는 manifest 신원·해시·경로에 대응하는 CSV 검토 결과를 새 JSONL에 반영한다. 명시적 존재/부재와 인원수만 적용하고 빈칸으로 기존 라벨을 변경하지 않으며, 원본 이미지·manifest를 덮어쓰지 않는다. 인원수 검토와 bbox 좌표 검증은 별개이므로 기존 주석 좌표도 따로 보존한다. 검토 도구의 정합성 검사가 수동 라벨의 사실 여부를 증명하는 것은 아니다.

## 서버 대결·정답 경계

`server/logic.mjs`는 명시적 라벨만 출제에 쓰고 SHA/원본 그룹을 연결해 한 격자에 같은 계보가 반복되지 않게 한다. 나무의 정확 수가 없더라도 명확한 `treeAtLeast3` 또는 3 이상의 하한은 양성 근거가 된다. 하한 2나 미주석을 음성으로 만들지 않는다. 모든 유형의 최소 양성/음성 그룹이 준비돼야 시작할 수 있다.

`server/service.ts`는 8자리 대기실 코드와 역할별 256-bit 토큰을 사용하며 DB에는 토큰 해시만 저장한다. 사람 역할만 시작하고 봇은 별도 준비 상태를 확인한다. 서버가 미래 공통 `startAt`을 정하며 클라이언트가 보낸 경과 시간으로 승패를 정하지 않는다. 최신 계약은 **서버가 먼저 수락한 완벽 정답을 즉시 승자로 고정**하고 오답에는 재제출을 허용하는 것이다. D1 batch와 revision/승리 조건으로 중복 시작·승리 덮어쓰기를 막는다. [D1 batch의 순차 트랜잭션 계약](https://developers.cloudflare.com/d1/worker-api/d1-database/#batch)을 사용한다. 초기 각 1회 제출 구현은 폐기하며 변경 검증/재배포의 실제 결과는 STATUS를 따른다. 90초는 현재 운영 가안이고 사용자가 확정한 시간 제한이 아니다.

공개 state는 phase/round/startAt·공개 질문/조건과 임시 타일 ID/URL을 담는다. 원격 방은 아래의 엔진 생존·선택 표시 상태도 별도로 제공한다. `answer_json`, 정답 개수, 원본 사진 ID·라벨·그룹·출처 메타데이터·토큰 해시는 반환하지 않는다. loading/countdown에는 화면의 질문/타일을 숨긴다. 준비용 preloadTiles는 loading부터, 공개 조건 preloadTopic은 countdown부터 제공하며 클라이언트가 같은 공통 startAt에 숨김을 해제한다. 사진 endpoint는 현재 라운드의 loading부터 디코딩을 허용한다. 만료 대기실·이전 라운드는 차단하되 이미 생성한 현재 라운드 사진은 이후 비활성화해도 유지한다. 새 출제만 활성 은행을 사용한다. 자신의 오답/승리 결과 공개는 채점 결과이며 정답 타일 목록 공개가 아니다.

운영자 API는 서버에 설정한 정확한 SIWC 소유자 ID와 Sites dispatch가 주입한 인증 헤더를 비교하거나, 비공개 관리자 키를 검증한다. 사용자가 보낸 본문/query의 ID·email·role로 관리자 권한을 주지 않는다. 공식 dispatch의 헤더 신뢰 경로를 전제로 하며 로컬 mock은 loopback에서만 작동하고 수신 인증 헤더를 먼저 제거한다. 관리자 키·역할 토큰은 공개 로그/URL query/버전 관리 파일에 저장하지 않는다.

사진 메타데이터·대기실·라운드는 D1, 사진 바이트는 R2에 저장하며 프로세스 전역 메모리를 정본으로 삼지 않는다. R2 put 후 D1 insert 실패 시 해당 object를 삭제하지만, 두 저장소 사이의 프로세스 강제 중단까지 하나의 분산 트랜잭션으로 묶은 것은 아니다. 누락/고아 object의 운영 점검은 별도다. [R2의 강한 read-after-write 일관성](https://developers.cloudflare.com/r2/reference/consistency/)과 이 앱의 DB/object 간 정합성을 구분한다. 이미지 업로드의 magic-byte 검사를 완전한 픽셀 디코딩·라벨 사실 보증으로 표현하지 않는다. 원본 이미지 내부의 EXIF/comment 제거도 아직 없으므로 서버의 private 채점 JSON을 숨기는 것과 모든 내장 메타데이터의 익명화를 구분한다.

## 로컬 시연과 나무 계수 후보

기존 Kaggle 134장 중 **34장·2,921,524 bytes**를 `data/booth/demo-images/`에 원본 그대로 복사했고 `demo-bank.json`은 비공개 정답/출처 기록이다. `prepare_booth_demo.py`와 localhost 전용 `import_booth_demo.py`를 사용한다. 이 사진의 일괄 공개 재배포 권한은 확인하지 않았으므로 기존 로컬 전용 제한을 유지한다. 최초 운영 게시 시점의 빈 은행·준비 안내는 이 제한의 결과이며, 이번 별도 공개 사진 등록의 실제 수량·준비 상태는 STATUS를 따른다. 학교 사진은 0장이고 train/val/test의 시연 재사용은 독립 정확도·40% 검증이 아니다.

사용자는 이어 웹에서 임의 사진을 받아 실제 사이트에 넣고 직접 시험하도록 요청했다. 공개 웹 시연 자료는 `data/booth/public-web-v1/`의 별도 은행으로 관리하며 기존 Kaggle 개발 정본·학교 최종 평가와 합치지 않는다. 사진별 출처 URL·저작자·공개 사용 근거·SHA·원본 그룹과 시각 검토 라벨을 보존한다. 사람 수·나무3그루 이상·건물·연못의 알려진 양성/음성만 출제에 쓰고 모호값은 null로 둔다. 같은 원본·연속 촬영·크롭 관계는 한 격자에 중복하지 않는다. 등록용 라벨은 서버 채점 자료이며 모델 입력이 아니다. 웹 시연을 위해 받은 사진을 새 학습·val·40% audit로 자동 편입하지 않고 모델·임계값도 바꾸지 않는다. 실제 확보·운영 업로드·네 유형 준비성·사진 HTTP와 브라우저 확인 결과는 STATUS에 각각 기록한다.

10/26 당시 확보·검토한 공개 은행은 **24장·6,063,549 bytes·24개 원본 그룹**이었다. Commons의 사진 원문 라이선스와 출처를 확인한 Public domain/CC0만 포함하며, 건축물의 PD 표기와 사진 자체의 CC BY-SA를 혼동한 후보는 제외했다. NASA 원본과 Adam Cuerden 복원본의 크레딧도 구분해 보존했다. 전체 프레임의 약960px JPEG로 정리하면서 EXIF/comment를 제거했고 최종 바이트 SHA·Pillow 디코딩을 확인했다. 기존 R2의 원본 바이트 서빙 구조를 바꾼 것이 아니라, 당시 별도 은행의 사진 전처리다. 시각 라벨은 단일 Codex 검토이며 독립 사람 검수 완료가 아니다. 아래 수량 표는 당시 이력이며 최신 활성 은행은 상단의34장 교체와 STATUS를 따른다.

`runs/site-publish/public-photo-rounds-verification.json`은 별도의 QA 방7개 요청으로 네 유형의 실제 출제를 모두 확인했다. 각 유형9사진의 HTTP 픽셀 디코딩·9개 서로 다른 SHA/원본 그룹·두 호스트의 동일 startAt/타일·허용 정답 수 범위·공개 답안 필드 부재를 통과했다. 서버 검사기는 채점 자료를 가진 특권 QA 도구이며 ML 풀이기가 아니다. 정답 제출·모델 추론·OS 입력은 하지 않았다.

이어 Chrome의 별도 QA 방을 시작해 실제9사진의 `loaded=true`와 양수 자연 크기를 확인하고 전체 화면을 기록했다(`public-photo-browser-verification.json`, `public-photo-browser-full.png`). 봇 역할의 참가/준비 API는 화면 출제 확인을 위한 것이며 실제 ML 봇 실행이 아니다. 선택0·제출0·ML 실행0을 유지했고 원래 사용자 대기실은 시작하지 않았다. 공개 사진은 직접 시험할 수 있는 상태지만, 정답 완주·실제 ML 봇 클릭·40% 성능을 검증한 결과는 아니다.

이번 공개 업로더를 포함한 전체 Python105개(12.020초)·compileall·pip check가 통과했다. 기존 사이트 소스/런타임 버전2는 유지하고 운영 키만 같은 권한으로 갱신한 환경revision3을 재게시해 성공했다. 이는 새 모델·새 ML calibration v2가 아니다. 환경 재게시·사진 등록·브라우저 표시·모델 OS 입력을 각각 확인한다.

나무 >=3 후보는 `IDEA-Research/grounding-dino-tiny`, revision `a2bb814dd30d776dcf7e30523b00659f4f141c71`이다. 고정 가중치 **689,359,096 bytes**, SHA `1a2412ef99bd74bcd3c2a246fa1e48581f8889a1300c9051974741314fc042f3`와 Apache-2.0 조건은 `alpha-provenance.json`에 기록했다. `local_files_only=True`, `trust_remote_code=False`, safetensors를 사용하고 추론 중 모델을 내려받지 않는다.

프로젝트에서 이 모델을 학습하지 않았다. 고정 prompt `a tree.`, box 0.35·text 0.25·NMS IoU 0.45, 입력 크기 short edge 480/long edge 640으로 실제 box를 검출한 뒤 3개 이상인지 판정하는 zero-shot 후보다. 작은 관목·가림·겹침·중복 검출의 오류 가능성이 있으며 숲의 정확한 총수나 40% 성공을 보장하지 않는다. 데모 라벨은 정확 수가 불명확하면 null과 명시적 >=3 근거를 보존한다. Pi 4B 메모리/추론 속도와 ONNX 지원은 아직 검증하지 않았다.

## 기존 OS 화면 봇 실행기와 미완료 검증

`booth_bot.py`는 공개 `task_type/operator/n`과 화면 RGB를 받아 CSS gap을 뺀 9개의 사진을 실제 모델에 넣는다. `run_booth_bot.py`는 dry-run 기본이며 `--execute`를 명시해야 OS 클릭을 요청한다. 소유한 localhost/`bot.marulee.dev` 화면만 대상으로 설정하고 전면 창 제목·명시적 좌표 보정·변하지 않는 질문 영역과 공개 round 상태를 검사한다. 조건에 필요한 나무 모델이 없으면 계수를 추측하지 않고 중단한다.

`--room` 모드는 공개 phase/roundId/startAt/topic.condition만 추출해 동기화하며 tile URL/ID를 읽어 제출 API로 답하지 않는다. 봇 토큰을 메모리와 해당 브라우저 세션에 전달하고 로그에 출력하지 않는다. 기존 수동 준비 경로에 더해 **명시적 `--execute --ready` 경로**를 추가했다. 이 경로는 존재/사람/나무 모델을 모두 준비하고 직접 봇 역할로 참가한 뒤 보정된 ALPHA BOT 전면창·캡처 범위의 격자/guard/submit을 확인해야 `/ready`를 보낸다. 사진 공개 전의 화면 범위 확인이므로9개 문제 사진 로딩 완료나 연속 엔진 heartbeat를 보증하지 않는다. 로컬 봇 경로는 `/?role=bot`이고 role fragment는 페이지가 읽은 뒤 제거한다.

실제 문의 원인은 웹 봇 준비 표시와 별개인 로컬 실행 프로세스·실측 `.local.json` 설정 부재였다. 루트 `Start-Alpha-Bot.cmd`와 `scripts/start_booth_bot.ps1`은 사용자 수동 보정 후 새 방 코드로 CUDA/고정 나무 모델/한 판 실행을 시작한다. 기존 웹 참가가 있으면 역할을 다시 가져오지 않고 새 방을 안내한다. `calibrated=false`의 실제 실행은 모델/GUI 초기화 전 거부한다. startup 모델/연결/창 오류는 단계별 한국어 메시지와 비밀값 없는 `aborted.json`으로 기록한다. 기다리는 중 엔진이 실패하면 가능한 경우 로비 ready를 해제한다.

기존 OS Python 봇은 최초의 빈 선택 상태에서 한 번 모델 선택/제출하는 경로다. 웹의 오답 수정 재제출은 허용되지만 봇의 자동 재시도는 아직 없으며 정답을 맞추려고 출력 반전·클릭 누락을 하지 않는다. 이 CLI의 `--rounds`는 **1만 허용**하고 같은 runner의 같은 공개 question ID에 두 번째 execute도 거부한다. dry-run 후 최초 execute는 가능하다. 이 legacy 경로의 새 참가자는 새 room으로 연결하며 오답 후 선택이 남은 문제에 실행기를 재시작해 토글을 반전시키지 않는다. 아래 remote 지속 세션은 별도 경로다.

CSS의 600×600·gap 8 격자와 OS 물리 좌표는 다르므로 브라우저 창/배율/줌을 실측해야 한다. 문제·포커스·공개 상태가 바뀌거나 상대가 먼저 이기면 남은 클릭과 제출을 취소한다. 같은 scheduler는 공개 question ID가 바뀌어도 연속 타일 간 최소0.25초를 보존한다. 새 프로세스에서 이전 클릭 시각을 복구하는 기능은 없으므로 반복 현장 운영의 입력 상태 관리도 검증해야 한다. 클릭 호출 시각·정책 대기·추론·제출을 나눠 기록한다. 첫 클릭 지연 0초는 가안이며 제출은 현재 타일 간격 제한 밖이다.

앞선 봇 테스트 **15개**로 dry-run 무입력, RGB-only 전달, 간격·변경 중단·공개 상태 추출·나무 모델 lazy 연결·0타일 선택 시 제출 기록과 최신 한 판/동일 question 재시도 차단·상대 승리 중단을 검사했다. 마지막1개는 HTTP 식별 헤더와 토큰 전달 범위를 검사한다. 공개 서버에서 Python 기본UA403을 관측해 `AlphaCaptchaBoothBot/1.0`을 명시했으며 실제 PublicRoomSession의 bot호스트 참가·상태조회도 통과했다. 이 연결 검사에서는 준비·사진·관리·제출을 호출하지 않았고 결과에는 토큰/방신원을 저장하지 않았다. 이 테스트는 OS 클릭·실제 GUI 포커스·두 기기 동시 대결의 증거가 아니다. 이전 URL 확인 실패로 중단한 화면 시험을 이번 브라우저 연결 확인과 구분하며, 저장 이미지의 ML 실행·UI/API 검사·공개 사진 적용을 ML 봇의 실제 화면 입력 성공으로 합치지 않는다.

## 컴퓨터 브라우저 원격 경로 (10/27 구현·11/06 단일 운영)

사용자가 원격 선택·HTTP 엔진 제출을 승인해 `remote` 모드를 추가했다. 인간·봇 표시는 컴퓨터 브라우저에서 이 원격 경로를 유지한다. 현재single의 인간 화면은 `{mode:'remote'}`로 방을 만들며 서버가 내부 A를 채운다. 명시적인 A도 호환하고 B는 차단한다. 봇은 읽기 전용 viewer, PC는 별도 engine 참가 토큰으로 연결한다. 두 참가의 순서는 자유롭고 역할별 중복 참가·레인 불일치를 각각 거부한다. `{}`로 만드는 기존 방은 legacy 계약을 유지한다. 원격 선택은 OS 전면창·공유 커서에 의존하지 않는다.

이전 Android4대와 A/B4화면 계획은 현재 운영 요구가 아니다. 인간1·읽기 전용 AI 표시1의 두 화면과 PC ML1worker/1stream으로 운영한다. 물리 컴퓨터 대수·각 OS/브라우저 버전·실제 화면 크기/배율·현장 성능은 확정하거나 실측하지 않았다.1024×768·768×1024·1280×800의 기존 viewport 검사는 브라우저 크기 시뮬레이션이며 새 컴퓨터 표시 환경 전체의 동작을 증명하지 않는다.

통신은 브라우저·PC 엔진 각각과 공개 서버 사이의 HTTPS API다. remote 봇은 진행 중 계획을 받기 전125ms로 조회하고, 유효한 계획 수신 뒤에는500ms 상태조회와 서버시계 기반 재생을 사용한다. 인간 화면·그 외 단계는500ms이며 진행 중 요청을 겹쳐 보내지 않는다. 최신 엔진은 약3초 heartbeat와 라운드별 선택 계획1회 업로드 후 상태 관측만 수행하며, 계획 미지원 서버에서만 개별 선택/제출을 사용한다. PC끼리 raw TCP로 직접 연결하는 경로·전용 지속 소켓은 구현하지 않았다. 이전 urllib 읽기 검사는 HTTP/1.1이었고 현재 Python은 표준 http.client로 HTTP/1.1 연결을 재사용하며, 브라우저의 실제 HTTP/2·HTTP/3 협상은 측정하지 않았다. 따라서 모든 클라이언트 통신을 TCP라고 단정하지 않는다. 방/코드/토큰이 지속되는 애플리케이션 세션과 전송 연결의 수명도 구분한다.

같은 Python 환경의 공개 봇 홈 읽기 전용 GET은 HTTP200·`response.version=11`(HTTP/1.1)로 확인됐다. 해당 Python 요청의 응답 버전이며 브라우저의 프로토콜·GPU 성능을 측정한 결과가 아니다.

`arena_remote_rooms`는 room_id·lane·엔진 토큰 해시·생존 시각·stage·ready·protocol·선택/sequence/시각을 저장한다.0001 원격 테이블에 이어 `0002_mysterious_ravenous.sql`이 engine_protocol 기본1과 room의 요청ID/요청시각/만료시각/취소사유4열만 추가한다. `npm run db:generate`1회로 생성했으며 과거0000/0001과 기존 데이터는 보존한다. 준비는 viewer 참가·ready·15초 생존이 필요하고 새 사진 준비 출발에는 protocol3도 필수다. `gpuReservationSupported`는 이 보고 여부이며 물리 잠금이나 뷰어의 계속된 생존/사진 로딩 보증은 아니다. stage는 lobby의 ready, queued의 waiting_gpu/reserved, begin 뒤 loading_images/images_ready·공통출발 뒤 inferencing/selecting/submitted와 error다.

초기 상태 응답은 `engineHeartbeatReceived`로 최초 생존 확인과 만료를 구분한다. stage=connected·seen=null이면 엔진 참가만 끝나 첫 heartbeat를 기다리는 상태이며 ready가 아니다. 유효 heartbeat가 한 번 도착한 뒤15초를 넘기면 실제 끊김이다. 서버 projection은 D1 remote 읽기가 끝난 뒤 시각을 잡아 serverNow·engineConnected·bot.ready에 함께 사용한다. 기존에는 읽기 전에 잡은 now 뒤 다른 요청이 heartbeat를 갱신하면 새 seen이 now보다 미래로 보여 잠깐 false가 됐다. 비동기 읽기 중 heartbeat가 커밋되는 제어된 회귀 테스트로 이를 재현하고 수정했다. 미래 시각 거부와15초 경계는 유지하며 대기 구간을 늘리거나 실제 만료를 숨기지 않는다.

remote의 인간 전용 `POST /api/rooms/:id/next`는 종료 roundId를 받아 D1 batch에서 선택/sequence/시각·엔진 ready·시작 ticket을 초기화하고 같은 방을 lobby로 돌린다. 코드·토큰·lane·누적 round_number·과거 결과는 보존한다. 중복 next는 같은 마지막 round의 lobby에서만 무변경 ACK하며 queued/다음 round를 옛 next로 초기화할 수 없다. 인간/start는 expectedRevision에 묶여 round 없이 queued 요청만 만들고 엔진 begin에서 누적번호+1이 된다. legacy는 기존 round_number=0·한 방 한 판/직접 시작을 유지한다. 지속 라운드만의 변경에는 migration이 없었고 이번 GPU 예약은0002를 추가했다.

새 heartbeat는 protocolVersion3와 관측 roundId/roundNumber/requestId(null|UUID)를 SQL CAS에 묶는다. ticket은 active/result까지 유지해 begin 응답유실의 동일 round 재전송을 ACK하고 next/cancel에서 비운다. queued는 waiting_gpu/reserved/error만, ready는 lobby만, result는 같은 round의 submitted/inferencing/error만 허용한다. 구 protocol1/no-ticket heartbeat는 기존 진행판 완료를 위해 호환하지만 새 queue 시작은 protocol_upgrade_required로 거부한다. 결과와 다음 참가자·공개 revision·이전 사진 차단은 유지한다.

PC 엔진은 세 고정 모델을 한 번 불러 공개 질문과9개 사진을 받는다.9사진은 독립 공개 경로를 최대3개 병렬로 디코딩하고 원순서를 보존한다. 실패 시 시작한 작업을 모두 정리하고 추론을 중단한다. 불투명 URL은 바이트 전송에만 사용하고 모델에는 RGB와 일반 조건만 전달한다. 현재single은 worker의 CUDA stream1개에서 기존 배치로 추론·호출별 자원 대기하고 마지막 대기까지 끝나면 슬롯을 해제한 뒤 실제 예측 번호만 계획으로 보낸다. 기능 지원 flag·서버 제출 결과·계획은 모델 입력이 아니다. 기존 개별 선택/제출은 계획 미지원 서버의 호환 경로로 보존하고 sequence/250ms·중복·회차/생존 CAS를 유지한다.

### 불변 선택 계획과 시간 기준

`selectionPlanSupported=true`인 서버의 `plan` action은 `roundId`와 순서 있는 고유0..8 번호 배열만 받는다. 활성/공통출발 후·미제출·기존 개별 선택0·생존이 확인된 엔진만 라운드당 한 계획을 CAS로 등록한다. 동일 순서/동일 번호 재전송은 결과 뒤에도 원래 계획 ACK이며 다른 기존 계획은 `plan_conflict`, CAS 상태 경합은 `plan_changed`, 개별 선택/제출 혼용은 `plan_active`, 마감 전에 재생을 끝낼 수 없는 계획은 `plan_too_late`로 거부한다. 0개도 가짜 선택 없이 계획을 등록하고 수락500ms 뒤 한 번 제출한다.

round의 nullable `bot_plan_indices_json`, `bot_plan_start_at`, `bot_plan_submit_at`, `bot_plan_correct`4열을 추가하는 migration은 `0003_colorful_cassandra_nova.sql`이다. 기존0000~0002와 역할 토큰/과거 결과는 보존한다. 계획 시작은 수락500ms 뒤, 마지막 시각은 시작+`max(0,n-1)*250ms`여서 최대9개에서 총2.5초다. 이 값은 네트워크/모델/브라우저 시간을 포함한 실측이 아니다.

서버가 수락한 계획은 PC 연결 유실 뒤에도 서버 시각에 따라 투영·최종 정산한다. 읽기만으로 승패를 임의 보정하지 않고 D1 정산과 인간 제출의 원자 경합으로 더 이른 완벽 정답을 보존한다. 인간이 먼저 이기면 남은 선택을 공통 종료 시각에서 잘라 표시한다. 계획의 예정 번호는 봇/엔진의 읽기 전용 표시만 사용하며 인간 응답·모델 입력에 제공하지 않는다. 예정 `bot_plan_correct`는 서버 전용으로 유지하고 마감/경기 종료 뒤 새 정답을 만들지 않는다.

PC 보고서는 계획 업로드/ACK·`planned_selection_events`의 서버 예정 시각과 `selection_events`의 실제 개별 HTTP 전송을 분리한다. 계획 경로의 실제 개별 전송 배열은 비어 있으며0.25초 예정 간격을 실제 클릭·실제 브라우저 렌더링 간격으로 주장하지 않는다. `logical_submission_count=1`은 계획 수락에 포함한 논리 제출 한 번이며 `server_submission_observed`가 실제 서버 시도 관측이다. 모델/상태HTTP 시간의 schema2와 선택 전송 schema3 기록도 구분한다. 최종 서버 경합·계획 UI·실제 CUDA/HTTP·성능/배포 검증은 STATUS가 정본이다.

이전 v8의 `SharedModels`는 단일 추론 잠금으로 직렬 실행했다. A1은 추론 구간1.547초·대기 구간0.391초, B1은 추론 구간0.844초·대기 구간2.250초였다. 당시 `gpu_queue_seconds`는 잠금 대기와 최초 active 상태조회 HTTP를, `inference_seconds`는 모델 판별과 뒤의 active 조회 HTTP를 포함했다. 순수 GPU/ML 시간이나 현재 병렬 모드 성능이 아니다. 최신 모드·출력 동등성·조합별 시간/VRAM·현장 한계의 정본은 STATUS다.

이전v8의 GPU 잠금 대기는 startAt 뒤에 발생해 해당 AI와대결하는 참가자가 상대적으로 유리해질 수 있었다. 위 A1/B1은 그때의 상태조회 포함 샘플이며 순수 GPU 잠금 차이·현재 예약 방식의 성능·모든 경기의 공정성 보장으로 확대하지 않는다.

후속 승인을 받아 시작 요청을 경기 전 GPU 예약 큐에 넣는 구조를 구현했다. queued는 roundId/startAt/deadline/topic=null·tiles=[]·타이머0이며 누적번호는 그대로다. PC가 실행 모드의 자기 슬롯을 확보한 후 인증된 begin(requestId,roundNumber)을 보낸다. 서버는 현재 ticket/준비/생존/프로토콜/revision을 쓰기에 다시 검사해 D1 batch에서 딱 한 round의 loading을 만들고 세 역할의 사진 준비를 확인한 뒤2초 공통 startAt을 확정한다. 사람·AI가 같은 시각에 시작한 뒤 공개 RGB를 추론하고 예약을 해제한다. 현재single은 한 대결만 운영하며 선택 간격0.25초와 모델 호출별 자원 대기를 구분한다. dual 복구에서만 다른 방의 추론과 선택 진행이 겹칠 수 있다. 서버가 물리 GPU 잠금을 직접 조회하는 것은 아니므로 예약 획득 후 begin을 보내는 신뢰된 PC 엔진과 함께 검증한다. 사전 풀이·타이머 사후 보정·임의 오답은 없으며 사용자 요청의30% 자원 대기는 별도 기록한다. 최종 실제 GPU/HTTP/UI/배포 결과는 STATUS다.

인간 cancel-start(requestId), queued 중 engine error·15초 생존 만료·120초 요청 만료(운영 가안)는 원자 lobby 복귀와 ready0으로 처리한다. 취소사유는 human_cancelled/engine_disconnected/engine_error/queue_expired다. 자동취소는 읽었던 heartbeat/stage도 CAS해 새 생존과 경합한 낡은 읽기가 현재 작업을 지우지 않게 한다. begin/HB 쓰기 전에 만료를 정산하므로 옛 ticket이 부활하지 않고 같은 방에서 재준비·사람의 새 수동 start만 허용한다. 취소/새 queue/동시 begin 경합은 revision·ticket·round counter로 격리하며 begin 재전송은 같은 active/result의 기존 round만 ACK한다.

엔진 제출은 서버에 저장한 선택 배열을 기존9타일에 매핑해 채점한다. 선택 snapshot의 배열·sequence와 요청의 실제 엔진 해시를 CAS 조건에 넣어 추론 후 선택 경합·낡은 권한을 거부하고, 기존 D1 batch의 첫 완벽 정답 단일 승자 규칙을 사용한다. 봇 viewer는 사진 준비 ACK만 할 수 있고 엔진 준비·선택·HTTP 제출은 금지되며 인간 공개 상태에는 `selectedIndices`를 제공하지 않는다. 봇 브라우저는 별도 봇 상태에서 서버가 수락한 선택만 표시한다. 물리 OS 마우스 제어나 화면 캡처 성공을 이 경로의 증거로 주장하지 않는다.

현재 엔진은 **라운드마다** 예측1회·제출1회이고 같은 문제의 오답 재추론/수정은 없다. 컴퓨터 브라우저 운영은 SETUP의 현장 순서를 따른다. PC 전원/인터넷과 인간·AI 표시 기본2주소를 준비하고 `Start-Alpha-Remote.cmd`에서3모델을 한 번 불러온 뒤 최초에만 인간 새 방→AI 표시→PC의 숨김8자리 코드로 연결한다. 이미 정상 대기 중인 엔진은 유지한다. 이후 첫 정답/현재90초 종료→인간 결과의 다음 참가자 준비→같은 엔진 ready→다음 사람 시작으로 반복한다. 새 코드·재참가·모델 다시 로드 없이 한 구역을 운영한다. 끝낼 때 quit/창 닫기로 종료하며 실제 게시·PC 재시작/가동은 STATUS가 정본이다.

## 학교 사진과 운영 자료 격리
사용자는 학교 사진을 이번 행사에 넣지 않기로 했다. 운영 문제와 평가에 학교 사진을 추가하지 않고 학교 최종 평가는 현재 행사 범위에서 제외한다. 운영 사진은 사용 허가·RGB 라벨·원본 그룹을 검토한 인터넷 자료로 별도 관리한다. 향후 학교 사진과 크롭·증강본을 별도로 취급하더라도 기존 개발 격리를 유지해 학습·미세조정·검증·모델 선택·조기 종료·임계값/전처리 튜닝에 사용하지 않는다. 개발 train/val/test의 Kaggle 자료와 운영 사진도 자동으로 합치지 않는다.

모델에는 RGB 픽셀과 문제의 일반 조건만 전달한다. 정답 파일·정답이 드러나는 경로/파일명·사이트 내부 정답·학교 평가 라벨을 풀이에 쓰지 않는다. 실제 학습 경로는 manifest의 Kaggle 출처·허용 경로·해시·분할을 검사하고 train만 최적화한다. 학교 경로·경로 탈출·허용 범위를 벗어나는 심볼릭 링크/정션을 거부한다. 다만 이름을 바꿔 옮긴 사진의 실제 출처까지 자동 판별하지는 못하므로 원본 출처·관계 기록과 별도 학교 평가 목록도 유지한다.

## 학습 제한과 속도 제한
v1 존재 판별기는 최대 train 64장·실제 41장·batch 8·1 epoch·6 step·AdamW lr 0.001이다. 사람 검출기는 최대 32장·실제 17장·batch 2·1 epoch·9 step·AdamW lr 0.0001이다. seed는 둘 다 42다. 사전학습 가중치의 이름·출처·해시, manifest 해시, 실제 예산과 학습 전 고정 프로필을 남겼다. presence 프로필은 `runs/frozen-profiles/`, person 프로필은 해당 출력의 `frozen-profile.json`에 있다. 이전 클래스당 200장·1~3 epoch 가안은 적용하지 않았다.

학습에는 train만 사용했고 임계값은 val 튜닝 없이 고정했다. v1 test 결과를 이미 확인했으므로 같은 test에 맞춰 모델·프로필·전처리·임계값을 다시 조절하지 않는다. 학교 평가나 본선 승패로 인간 승률을 맞추지 않는다.

### v2 선택과 최종 audit

v2에서는 v1 test와 그 복제·연속 촬영·크롭 관계 그룹을 학습·선택·새 audit에서 격리한다. 새 Kaggle 자료를 source-group 단위로 train/선택용 val/미사용 audit로 나누고 라벨 규칙·조건/n·격자·seed·비교할 제한 예산 목록을 예측 전에 기록한다. unknown을 음성이나 0명으로 바꿔 자료 부족을 메우지 않는다. 현재 연못 양성과 높은 인원 조건의 적격 자료는 이 검증에 부족하다.

격자 생성기는 채점용 라벨로 4정답·5오답과 서로 다른 그룹 9개를 확인한다. 모델/선택기는 RGB와 공개 조건만 받아 고정 임계값과 count 비교로 선택한다. 채점기는 그 뒤 실제 선택 집합과 정답 집합을 완전히 대조한다. 정답 수·정답 ID·문제 ID별 답 조회를 predictor 입력으로 넣지 않는다. 결과를 본 뒤 격자를 골라 목표 성공률을 만들지 않는다.

현재 구현한 캐시 평가기는 `scripts/evaluate_grids.py`의 adapt-presence/adapt-person/evaluate 경로로 기존 v1 val 예측을 읽는다. 기본 disjoint 모드는 격자 사이에도 그룹을 재사용하지 않으며 reuse 모드는 재사용·고유 그룹/사진/구성 수를 남긴다. 어느 모드도 현재 `target_achieved`나 독립 성공률 신뢰구간을 자동 판정하지 않는다. 서명 없는 캐시의 해시 정합성 검사는 그 예측이 실제 모델에서 나왔다는 진정성 증명은 아니다. 새 v2는 `plan_validation_grids`로 은행을 예측 전에 별도로 고정해야 하며, 이미 있는 v1 예측의 재생을 이 실험으로 부르지 않는다.

비교 실험에서는 CLI 기본값 또는 API의 `evaluate_test=False`로 test 평가를 생략한다. `--evaluate-test`나 직접 API의 `True`는 명시적 평가이며, 기존 v1 test를 v2에 써도 된다는 허가는 아니다. 미평가 모드는 test의 모델 추론과 평가 결과 생성을 막으며 manifest 구조·해시·분할 정합성 검사는 별개로 수행한다. 합성 CPU 테스트는 test evaluator가 호출되지 않고 report/체크포인트에 `test_evaluated=false`가 남으며 test 지표·예측 파일이 없는지 검증했다. 실제 새 audit를 평가한 것은 아니다.

제한 후보는 선택용 val에서만 비교하고 선택한 모델의 가중치·설정 해시를 고정한 후 새 audit를 한 번 평가한다. 학습량만 줄여서 모든 조건을 약 40%로 맞출 수 있다고 가정하지 않는다. 미달 조건은 공개하고 동일 audit나 학교 결과로 다시 조절하지 않는다. 두 모델을 공유하므로 사람 수 n별 실패와 존재 과제별 실패를 전체 평균으로 숨기지 않는다.

학습량 제한은 의도한 정답률을 정확히 보장하지 않으므로 Kaggle val에서 실제 성공률을 확인한다. 경기에는 명시적 클릭 속도 제한을 별도로 적용한다. 추론 등 앞선 처리가 이미 대기 시간을 넘겼으면 다음 콜백을 위해 무조건0.25초를 추가하지 않는다. 실제 클릭 간격·추론 시간·정책 대기 시간·총 시간을 분리해 기록한다. 9칸이므로 무조건 9초가 걸린다고 단정하지 않는다.

현재 스케줄러는 한 콜백이 최대 한 번의 타일 클릭을 동기적으로 수행한다는 계약을 갖는다. 콜백 내부에서 클릭이 늦게 발생할 수 있어 콜백 **종료 시각**을 다음 허용 시각의 보수적 기준으로 사용한다. 지연 뒤 몰아 실행하지 않고, 문제 토큰 교체·취소 시 이전 큐를 중단하며 직전 시각은 문제 사이에도 보존한다. 실패한 콜백도 이미 클릭했을 가능성이 있으므로 다음 간격 제한에 포함한다. 시계 역행·잘못된 시계값은 후속 실행을 차단한다.

첫 클릭 대기 기본값0초는 가안이며 설정으로 명시한다. 제출은 현재 타일 스케줄러 범위에서 제외한다. 경기 종료/재제출은 위의 참가자별 한 라운드 규칙을 따르며 첫 클릭/제출의 별도 지연과 운영 시간 제한은 아직 확정하지 않았다. dry-run의0/0.25/0.5초는 이전 클릭·처리 지연이 없는 계획이며 실측 시간이 아니다. 콜백 성공 기록도 OS 입력 성공을 입증하지 않는다.

## 모델 배포와 전처리 계약
실제 체크포인트는 `models/checkpoints/presence-limited-v1/presence.pt`와 `models/checkpoints/person-limited-v1/person.pt`다. 각 출력의 `report.json`에 프로필·가중치/데이터/모델 해시·손실·기기·시간과 평가를 기록했다. 두 로더는 `weights_only=True`로 읽고 사전학습 재다운로드 없이 모델을 복원한다.

존재 판별은 전체 RGB 사진을 224×224 letterbox로 넣고 ImageNet mean/std로 정규화한다. 사람 검출은 320×320 letterbox와 고정 패딩을 사용하고 검출 좌표를 원본 픽셀로 되돌린다. 중앙 크롭은 사용하지 않는다. 전처리·클래스 순서·logits/sigmoid·score/box/count·임계값·NMS 계약은 PyTorch 학습과 추론에 구현했다. ONNX 입출력 이름·형상·opset과 출력 동등성 검증은 아직 없다.

내보내기 후 동일한 Kaggle 입력으로 PyTorch/ONNX의 수치·검출 후처리·사람 수·선택 타일 결과를 대조한다. 작은 수치 차이가 임계값 또는 n명 경계에서 답을 바꾸는지 별도 확인한다. PC와 Pi에 같은 고정 모델과 metadata를 배포한다.

## Pi와 검증 기준
사용자는 PC와 Pi를 시리얼 어댑터로 연결할 수 있다고 했다. 연결되면 시리얼 셸로 OS·ARM64·Python·RAM·세션·패키지 정보를 빠르게 확인한다. 실제 COM 포트·전송 속도·OS·그래픽 세션은 아직 미확인이다. 시리얼 셸 연결은 화면 전송이나 GUI 캡처/클릭 지원을 자동 보장하지 않는다. 저장 이미지 추론, 캡처, 입력, 클릭 간격은 별도로 검증한다.

앞선 Windows `Get-CimInstance Win32_SerialPort` 조회에는 인식된 포트 목록이 없었다. 이 결과만으로 물리적 연결 여부나 Pi 상태를 단정하지 않는다. Pi 접속과 실기기 추론·입력은 아직 확인하지 않았다.

v1의 작은 Kaggle test에서 알려진 라벨 기준 tree F1은 약 0.667·accuracy 0.5였지만 모든 타일을 양성으로 예측했다. building은 F1 약 0.824·accuracy 0.8이었다. pond는 알려진 11장 중 양성 1장을 놓쳐 recall 0이며 모든 타일을 음성으로 예측했다. unknown은 지표 분모에서 제외했다. **이 존재 판별기를 부스용 완성 모델로 보지 않는다.** 사람 계수 test는 exact 13/18, MAE 약 0.556이지만 작은 COCO 표본이고 COCO 사전학습 이력이 있어 학교 성능으로 일반화하지 않는다. 마지막 사람 없는 단독 학습 batch의 SSD loss 0도 음성 학습의 한계로 기록했다.

저장 3×3 격자의 두 모델 GPU 추론·전처리를 한 번 실행해 약 0.56초와 선택 타일 8의 좌표·예정 시각을 확인했다. 이는 모델 로드와 화면·클릭·제출을 포함한 경기 시간이나 p50/p95가 아니다. 학교 최종 평가, Pi 속도, 실제 입력 간격과 충분한 독립 격자의 전체 문제 완전 일치율은 미측정이다.

기존 v1 val 예측 캐시를 seed 20261022로 재생해 8조건에 각각 100개 disjoint 격자를 요청했다. 건물만 1개·0/1 성공이며 다른 7조건은 0개다. 전부 자료 부족, `target_achieved=null`이므로 40% 달성 여부를 판단할 수 없다. `runs/calibration-v2/validation-grid-summary.json`이 이 집계의 정본이며 새 모델 추론·학습·학교 평가가 아니다.

9칸 중 정답이 k칸인 문제의 선택 집합 완전 일치는 정답 k칸을 모두 선택하고 나머지 9−k칸을 모두 제외해야 한다. `P = TPR^k × TNR^(9−k)`는 각 타일의 오류가 독립이고 양성·음성 각각에 동일한 성능을 적용할 수 있다는 가정 아래의 대입값이다. 공통 배경·사진 분포 차이·작은 평가 표본의 영향을 반영한 학교/부스 실측값이 아니다. 구체적인 가정 분석은 [STATUS.md](STATUS.md)를 따르며 이 계산으로 기존 v1 모델을 조정하지 않는다.

v2의 4정답 격자도 실제 exact-set 성공 횟수/문제 수와 양성 TPR·음성 TNR·FP/FN을 함께 보고한다. 같은 사진을 여러 격자에 재사용하면 오류가 연결되므로 그 격자 수를 독립 문제 표본 수로 취급하지 않는다. 독립 격자·원본 그룹 수·재사용량과 조건별 분모를 구분하고, 허용오차 미정 상태에서 40% 달성을 자동 판정하지 않는다. v1 한 장 통합 점검·기존 예측 재생과 새 모델의 독립 audit는 서로 다른 검증이다.
