사진 준비에는 추가 migration `0004_amazing_namora.sql`이 round의 준비 번호/만료 시각/세 역할 준비 플래그5열을 더한다. 기존0000~0003은 변경하거나 다시 적용하지 않는다. 실제 로컬/운영 적용은 STATUS를 확인한다.

검증 스크립트 `scripts/verify_continuous_booth.py`는 실제 PC 모델을 한 번 로드해 A두판+B한판을 진행하고, 인간/봇 역할도 각각9개 공개 RGB를 실제 다운로드·PIL 디코딩한 뒤 준비를 알린다. A첫판 인간 준비를3초 보류해 PC/봇 준비 뒤에도 타이머0·사전 추론0인지 검사한다. 이 보류는 시험 조건이며 운영 지연 설정이 아니다. HTTP/PIL 시험은 실제 브라우저 렌더링 시험과 별개다. 같은 RGB의 출력 동등성과 준비/모델/HTTP 시간, 경기 중 사진 다운로드0을 기록하며 독립 정확도·목표40% 달성이나 지연0을 주장하지 않는다. 실제 게시/실측·현장 기기/네트워크의 미확인 범위는 STATUS가 정본이다.

## 공개 API와 인증

룸 API는 역할 토큰을 `Authorization: Bearer <token>`으로 받는다. 생성·참가 응답의 토큰은 브라우저 메모리/`sessionStorage`에서 관리하고 문서·로그에 남기지 않는다. 기존 OS 봇 실행기가 브라우저에 전달할 때만 `#room=...&token=...` fragment를 사용하며 페이지는 이를 읽은 직후 URL에서 제거한다. remote 엔진 토큰은 PC 메모리에만 두고 봇 표시 브라우저에 전달하지 않는다. 로컬 봇 URL에는 `?role=bot`을 사용하고 배포 봇 호스트는 역할을 자동으로 정한다.

| 경로 | 요청·역할 | 응답과 동작 |
|---|---|---|
| `POST /api/rooms` | `{}` 또는 `{mode:"remote",lane:"A"|"B"}` | 각각 기존/원격 인간 방 생성, `{roomId, code, token, state}`. 연결 코드는8자리 |
| `POST /api/rooms/join` | `{code,role:"bot"|"engine",lane?:"A"|"B"}` | bot은 기존 봇 또는 원격 읽기 전용 표시 역할. engine은 원격 방에만 별도 최초 참가. 레인 불일치409 |
| `GET /api/rooms/:id` | 역할 토큰 | 해당 역할의 공개 상태 |
| `POST /api/rooms/:id/ready` | `{ready:true}` | 기존 역할 준비 상태 변경. 원격 bot/engine은403이며 엔진 heartbeat로만 준비 |
| `POST /api/rooms/:id/start` | remote 인간 `{expectedRevision}`, legacy `{}` | remote는 준비된 lobby에 queued 요청만 생성. round/타이머는 아직 없음. legacy는 기존 한 방 한 판 직접 시작 |
| `POST /api/rooms/:id/cancel-start` | remote 인간 `{requestId}` | 현재 queued/loading/출발 전 countdown을 취소하고 lobby·ready0. 시작/다른 요청으로 바뀌면409 |
| `POST /api/rooms/:id/next` | remote 인간, `{roundId:종료roundId}` | result→lobby 원자 초기화, 같은 방/코드/토큰 유지. 같은 마지막 round의 lobby 중복은 무변경 ACK, 낡은 요청은409 |
| `POST /api/rooms/:id/submit` | 인간 또는 기존 봇, `{roundId,tileIds:[...]}` | 배열 중복·다른 문제·종료 후 제출 거부. 원격 bot/engine 토큰은403. 오답은 같은 라운드 재제출 허용 |
| `POST /api/rooms/:id/engine` | 원격 엔진, 아래 action | heartbeat·GPU begin·불변 선택계획과 개별선택 호환. 계획 최소ACK는 `{plan,serverNow}`이며 정답/미래correct는 없음 |
| `POST /api/rooms/:id/images-ready` | 인간/봇 표시, `{roundId,requestId,imageLoadId,ready,failed?}` | 현재 라운드 준비 번호에만 등록/디코딩 ACK. 봇의 답안 선택 권한은 없음 |
| `GET /api/photos/:id` | 현재 라운드의 loading 이후 불투명 타일 ID | 이미지 픽셀만 제공. 원본 파일명·출처·라벨·정답 정보 없음 |

공개 상태는 `serverNow`, `roomId`, `code`, `phase`, `roundId`, 누적 `roundNumber`, `revision`, `startAt`, `deadlineAt`, 공개 `topic`, 사진 `tiles`, 양측 준비·제출 상태와 결과를 포함한다. `phase`는 `lobby/queued/loading/countdown/playing/result`다. remote의 `startRequest={id,requestedAt,expiresAt}|null`과 `lastStartCancellationReason`도 제공한다. queued는 roundId/startAt/deadlineAt/topic=null·tiles=[]이며 누적번호를 유지하고 타이머0이다. loading부터 준비용 preloadTiles, countdown부터 preloadTopic을 제공하되 화면에서는 공통 시작까지 숨긴다. 정답·라벨·원본 경로는 계속 숨긴다. 자기 오답은 `correct=false`, `submitted=false`, `phase=playing`으로 계속 수정하며 최근 오답 elapsedMs로 타이머를 멈추지 않는다. revision은 늦은 상태 응답을 구분하는 번호이고 정답 정보가 아니다.

종료 결과에는 `winner`, 공통 종료 Unix ms인 `finishedAt`, 공통 경과 시간 `elapsedMs`, `reason=correct/timeout`을 기록한다. 첫 정답은 서버 동시성 제어로 한 승자만 확정하고 즉시 `phase=result`가 된다. 화면은 상태 수신 후 양쪽 입력을 잠그고 공통 종료 시간으로 타이머를 멈춘다. 상대 승리 알림에는 인간/그 외 단계500ms·remote 봇의 계획 수신 전125ms/수신 후500ms 폴링과 네트워크 지연이 있지만 서버는 이미 종료된 방의 제출을 채점하지 않는다. 점수표에는 승리 정답 시각을 사용하며 오답 시각을 완주 시간으로 표시하지 않는다.

결과의 **‘다음 참가자 준비’**는 remote 인간만 호출한다. 서버는 종료 roundId·현재 revision·result를 검증한 D1 batch에서 선택 배열·sequence·마지막 선택 시각·엔진 ready를 비우고 stage=connected, room.phase=lobby, round_id=null로 만든다. 코드·engine/viewer 토큰·lane·누적 roundNumber·과거 결과는 보존한다. 같은 마지막 roundId의 lobby 재요청은 상태를 다시 비우지 않고 ACK한다. 새 active·새 result·다른 라운드에 대한 옛 next는409이며 엔진/뷰어 토큰은403이다. next와 다음 start가 경합해도 새 선택/준비를 지우지 않는다. 그 뒤 엔진이 새 lobby를 관측해 ready를 보내고 다음 사람이 시작해야 새 문제가 나온다. legacy는 기존 새 방·새 코드 경로를 유지한다.

remote 봇은 계획 수신 전125ms·유효 계획 수신 후500ms 상태조회를 예약하고 서버시계로 선택을 재생한다. 인간 화면과 그 외 단계는500ms이며 이전 요청과 겹쳐 보내지 않는다. 각 화면은 `performance.now()`와 최근 최저 RTT 응답의 중간 시각/`serverNow` 차이로 표시 시계를 보정하고, 확정된 카운트다운에서는 기준을 고정한다. 준비된 remote는 같은 이미지/질문을 startAt에 공개하므로 출발 직후 추가GET 응답을 기다리지 않는다. legacy의 공개 질문 조회는 별도 호환 경로다. 실제 출발·제출·종료 판정은 서버 시각이 기준이며 클라이언트 타이머가 승패를 결정하지 않는다. 실제 네트워크·렌더링 지연은 별도로 기록해야 한다.

통신은 브라우저와PC 엔진이 각각 공개 서버에 보내는 HTTPS API 요청이다. 엔진 heartbeat 기본 주기는 약3초이며 요청 처리 시간·네트워크 지연이 더해질 수 있다. PC끼리 raw TCP로 직접 연결하거나 전용 지속 소켓으로 상태를 보내는 계약은 없다. 이전 urllib 조회는 HTTP/1.1이었고 현재 PC는 표준 http.client로 HTTP/1.1 연결을 스레드별 재사용한다. 브라우저가 실제로 HTTP/2 또는HTTP/3을 협상했는지는 측정하지 않았으므로 모든 연결을 TCP로 단정하지 않는다. 같은 방/코드/토큰을 유지하는 지속 세션은 애플리케이션 상태의 지속이며 하나의 전송 연결을 계속 유지한다는 뜻이 아니다.

같은 Python 환경에서 공개 봇 홈을 읽기 전용 GET으로 조회한 응답은 HTTP200과 `response.version=11`(HTTP/1.1)이었다. 이 확인에는 방 참가·시작·모델 추론·운영 엔진 조작이 없었고 브라우저 협상 결과로 확대하지 않는다.

기존 OS 봇은 진행 상태·시작 시각·일반 조건만 사용하고 사진은 화면 캡처로 얻어 버튼을 클릭한다. 새 remote 엔진은 사용자 승인에 따라 같은 공개9사진 URL을 바이트 전송에만 사용한다. 불투명 URL/ID의 문자열 의미·정답·사진은행 메타데이터는 모델 입력이 아니며 RGB 픽셀과 일반 조건만 판별에 전달한다. 원격 선택/엔진 제출을 기존 OS 클릭 성공으로 보고하지 않는다.

## 관리자 사진 등록과 소유자 인증

`/admin`은 공식 `/signin-with-chatgpt?return_to=/admin` 일반 브라우저 이동과 ‘로그인된 소유자로 입장’ 버튼을 제공한다. 소유자 모드는 비밀키 없이 같은 origin의 `/api/admin/status`를 요청하고 서버가 **설정된 `ADMIN_OWNER_ID`와 Sites의 신뢰된 `oai-authenticated-user-id`가 정확히 일치하는지** 검사한다. 브라우저가 사용자 ID를 만들어 보내지 않는다. 소유자 설정·로그인·일치 검증이 실패하면 접근을 열지 않는다. 배포 환경의 실제 소유자 로그인 검증은 별도로 기록한다.

기존 `ADMIN_KEY` 인증은 관리자 비밀번호 대체 경로와 CLI 용도로 유지하며 `x-admin-key` 헤더를 사용한다. 키를 URL·채팅·Markdown·파일에 넣어 배포 편의를 해결하지 않는다. 업로드와 미리보기도 같은 인증을 요구한다.

| 경로 | 용도 |
|---|---|
| `GET /api/admin/status` | 유형별 독립 양성·음성 그룹 수와 출제 준비 상태 |
| `GET /api/admin/photos` | 관리자에게만 활성 사진 메타데이터·active·SHA 제공. `?includeInactive=1`이면 비활성도 포함 |
| `POST /api/admin/photos` | multipart `file` + `metadata` JSON. JPEG/PNG/WebP, 장당 8MiB 이하 |
| `PUT /api/admin/photos` | 관리자 `{photoIds:[...]}`. 기존1~128개 고유 ID·전 유형 준비성을 검사하고 활성 집합 원자 교체 |
| `GET /api/admin/photos/:id` | 인증된 원본 미리보기. 화면은 인증 fetch의 blob URL을 사용 |

메타데이터에는 `personCount`, `treeCount`, `treeAtLeast3`, `building`, `pond`, `groupId`, `source`, `usageNote`를 기록한다. 모르는 수·존재는 null로 남긴다. 숲의 총 나무 수를 몰라도 3그루 이상이 명확하면 `treeCount=null`, `treeAtLeast3=true`로 기록하며 정확히 3그루라고 지어내지 않는다. 출처는 학교·Kaggle·기타 허가 자료로 구분하고 같은 원본/연속 촬영/크롭에 같은 그룹을 사용한다. 검토 체크 후 여러 사진을 차례로 등록하고, 일부 실패 시 등록된 수와 남은 사진을 구분한다. 서버도 값·모순·이미지 형식·중복 해시·그룹을 검사한다.

학교 사진은 최신 사용자 결정으로 이번 행사 문제은행과 최종 평가에 사용하지 않는다. 향후 학교 자료를 별도 취급하더라도 학습·개발 검증·모델 선택·전처리/임계값/예산 튜닝에 사용하지 않는 기존 격리 원칙을 유지한다. 공개 사용 조건과 실제 RGB 라벨을 검토한 인터넷 사진을 운영 자료로 추가하며 운영 라벨은 비공개 채점 자료다.

## 웹에서 확보한 공개 테스트 사진

사용자가 임의 웹 사진을 내려받아 사이트에 적용하도록 승인했다. 별도 `data/booth/public-web-v1/bank.json`에는 Public domain13장·CC0 11장의 웹 사진24장·24원본 그룹·6,063,549bytes와 출처·저자·원본 식별·허가 근거·다운로드 SHA를 기록했다. 이미지를 실제로 검토해 사람 수·나무 >=3·건물·연못을 라벨링하고 정확 수가 모호하면 null로 남겼다. 단일 AI 시각 검토이며 독립 사람 검수는 남아 있다. 실제24장 파일/SHA/디코딩/라벨의 importer dry-run 이후 **운영 사이트 등록24/24장·이미 등록0장·완료true**를 확인했다. `runs/site-publish/public-bank-upload.json`은 운영자 키 저장/로그0·학교0·공개 허가true를 기록한다. 이 사진은 학습·모델 튜닝에 사용하지 않았다. 공개 준비성·출제와 사진 HTTP/브라우저 표시·채점 결과는 STATUS의 후속 검증과 구분하며 업로드만으로 실제 ML 클릭까지 완료됐다고 보고하지 않는다.

`import_public_booth_bank.py`는 이 공개 은행을 `source=other`로 관리자 API에 등록하는 별도 운영 도구다. 기존 Kaggle 로컬 importer의 외부 업로드 차단은 유지한다. 기본 dry-run이며 `--execute --admin-key-stdin`을 명시해야 실제 등록한다. 외부 호스트·공개 도메인의 HTTP/비표준 포트·리다이렉트·경로 탈출·학교/Kaggle/미허가 은행·중복 ID/바이트·잘못된 SHA/이미지/라벨을 거부한다. 같은 원본/연속 촬영 관계의 서로 다른 사진은 은행에서 같은 그룹으로 허용하고, 서버 출제기가 한 격자에 같은 그룹을 중복 배치하지 않는다. 이미 등록된 동일 SHA의 `duplicate_photo`만 안전하게 건너뛰며 기존 라벨을 교체하지 않는다. 처리한 행은 키 없는 새 결과 파일에 남기므로 중간 실패 후에는 새 출력 경로로 재실행한다.

이 도구의 관리자 사진/정답 접근은 문제은행을 만드는 운영 단계다. 풀이기는 화면 또는 사용자 승인된 공개 사진 전송으로 얻은 RGB와 일반 공개 조건만 사용한다. 업로드 provenance가 서버에 보관돼도 공개 격자에 원본 제목·라벨·실제 정답 개수를 넣지 않는다. 웹 테스트 사진과 그 경기 결과를 학습·임계값 검색·목표40% 조정 자료로 자동 편입하지 않는다. 학교 사진·고정 후 최종평가와도 분리한다.

## 기존 OS 화면 픽셀·좌표 계약 (legacy)

이전 자동 클릭 문의에서 기존 OS 봇 프로세스와 실측 설정이 없음을 확인했다. 기존 봇 웹사이트의 수동 참가/준비는 프로세스를 실행하지 않으며, 그 준비 표시는 로컬 엔진 heartbeat가 아니다. `Start-Alpha-Bot.cmd` → `scripts/start_booth_bot.ps1` → `run_booth_bot.py`의 Windows 실행 경로를 추가했다. 첫 실행의 수동 F8 보정은 사용자가 직접 수행하고 실제 설정이 생기기 전에는 `calibrated=true`를 자동 생성하지 않는다. 현재 별도 원격 엔진 가동과 생존 확인은 다음 remote 계약 및 STATUS를 따른다.

실행기는 웹에서 수동 참가하기 전 새 방 코드로 직접 참가한다. 기존 봇 참가가 있으면409 `bot_already_connected`를 새 방 안내로 변환하며 저장소의 역할 토큰을 읽거나 역할을 탈취하지 않는다. 기본 `--execute --ready`는 존재/사람/나무 모델 로드 후 보정된 전면 창과 캡처 범위 내 격자·guard·제출 좌표를 확인하고 `/ready`를 호출한다. `--ready` 없는 기존 CLI는 수동 준비를 유지하며 dry-run은 자동 ready를 보낼 수 없다. 준비 후에도 프로세스가 계속 살아 있음을 서버가 보증하는 heartbeat는 추가하지 않았다.

한 판 후 프로세스가 종료되고 다음 참가자는 새 방/새 실행이다. 같은 PC에서 인간 화면을 눌러 시작하면 전면창이 바뀌므로 봇 창으로 복귀하거나 인간은 패드에서 시작해야 한다. 초기 모델 실패/서버 오류/창 확인 문제는 토큰 없는 `aborted.json`의 stage·오류 종류와 한국어 안내로 남긴다. 이 준비·진단 경로의 합성 검증과 실제 OS 입력 검증은 별개다.

봇 페이지 제목은 `ALPHA BOT | CAPTCHA`다. 봇 격자는 CSS 600×600px, 가로·세로 간격 8px, 3×3이며 사진은 `object-fit:contain`으로 전체를 표시한다. 선택 표시만 테두리와 체크로 덧씌우고 사진의 opacity/filter를 바꾸지 않는다. 이미지 URL은 불투명 ID, alt/접근성 이름은 단순 사진 번호다. 페이지 JavaScript가 정답을 선택하지 않는다.

CSS viewport 좌표를 OS 물리 좌표로 바로 사용하지 않는다. 이번 관측에서는 봇 페이지의 제출 버튼이 브라우저 viewport 밖으로 내려가 있었으며, 이전 설계의 고정 y좌표도 실제 실행 설정으로 사용할 수 없다. 수동 보정은 **사진9칸과 제출 버튼이 동시에 보이는 주 모니터**에서 진행한다. 다음 표는 저장할 영역의 의미이며 좌표 예시가 아니다.

| 영역 | 실측할 내용 |
|---|---|
| 격자 | 전체3×3 격자의 실제 좌상단/우하단과 타일 간 물리픽셀 간격 |
| 질문 보호 ROI | 질문 제목·설명만 포함하는 실제 사각형. 타이머/선택수/움직이는 부분은 제외 |
| 제출 버튼 중심 | 보정한 상태에서 실제로 화면 안에 보이는 버튼 중심 |

실행 전 브라우저 chrome 높이·창 위치·스크롤·OS 배율·브라우저 줌·모니터를 포함해 물리 캡처 좌표를 보정하고 `calibrated=true`인 별도 설정에 기록한다. 기본 예시 좌표를 보정 없이 클릭하지 않는다. 타일 순서는 왼쪽 위부터 행 우선 0..8이고 실제 캡처에서는 간격 8px을 제거해 독립 사진을 모델에 넣는다. 화면 크기와 보호 ROI가 맞지 않거나 대상 ALPHA 창이 전면이 아니면 중단한다.

`run_booth_bot.py`는 기본 한 라운드만 처리한다. 참가자 교체는 새 방·새 코드로 연결하며 `--rounds`가 같은 방 재시작을 허용한다는 뜻은 아니다. 현재 단일 실행은 한 번의 모델 선택·제출 경로이고 오답 후 자동 재추론·재제출 정책까지 검증한 것은 아니다. 임의 예측 반전으로 재도전하지 않는다. 질문 영역·공개 라운드가 바뀌거나 상대 승리로 종료되면 남은 입력을 취소해야 한다. 출력은 새 디렉터리만 허용하고 캡처·선택·입력 시각·제출 여부·중단 원인을 기록하며 역할 토큰은 남기지 않는다.

## 컴퓨터 브라우저·A/B 원격 연동 계약 (10/27 후속 변경)

각 레인은 컴퓨터 브라우저의 인간 화면1개·봇 표시 화면1개와 별도 방/코드를 사용하고 **최초 한 번만 페어링**한다. 같은 방 안에서 라운드별로 참가자를 교체한다. `?lane=A`/`?lane=B`와 UI 역할·레인 세션을 구분하며 PC 모델은 한 번 불러 공유한다. 현장 운영 순서는 SETUP을 따른다. viewer와 engine은 독립된 최초 토큰을 받고 순서는 자유롭다. 중복 viewer는 `bot_already_connected`, 중복 engine은 `engine_already_connected`, optional lane 불일치는 mutation 전에 `lane_mismatch`409다. 봇 브라우저는 자기 사진 준비 ACK만 할 수 있고 엔진 준비·선택·제출·next 권한이 없다.

이전 Android 태블릿4대 계획은 컴퓨터 브라우저 운영 요청으로 대체됐다. 인간2화면·읽기 전용 봇2화면이라는 역할과 PC 추론/엔진 토큰 분리는 유지하며 물리 컴퓨터 대수·OS/브라우저 버전·실제 해상도/배율·현장 성능은 확인하지 않았다. 기존1024×768·768×1024·1280×800 viewport 확인은 브라우저 크기 시뮬레이션이며 Android 실물이나 새 컴퓨터 환경 전체의 입력·렌더링·네트워크 성능 검증이 아니다.

현장에서는 PC 전원 어댑터·인터넷과 컴퓨터 브라우저4화면을 준비하고 A/B별 인간 `human.marulee.dev/?lane=A|B`·표시 `bot.marulee.dev/?lane=A|B` 주소를 연다. 각 화면에 공개 HTTPS 인터넷 접속이 필요하며 같은 Wi-Fi를 필수로 요구하지 않는다. PC 원격 실행기의3모델 로드·합성 RGB 예열과 숨김 입력 대기를 확인한 뒤 최초에 인간 새 방 코드→같은 레인의 봇 표시 브라우저→PC 콘솔 `A 코드`/`B 코드`와 Enter로 연결한다. 이미 정상 대기 중인 엔진은 유지한다. 숨김 입력 때문에 타이핑이 보이지 않는 것이 정상이며 F8 보정은 사용하지 않는다. 인간은 봇 연결/첫 heartbeat/PC 준비가 확인된 뒤 시작한다.

첫 정답 또는 현재90초 종료 후 인간 결과 화면에서 ‘다음 참가자 준비’를 누르고 PC 재준비가 표시되면 다음 사람이 시작한다. 같은 방·코드·토큰과 모델을 유지하고 콘솔 재입력·모델 재로드는 하지 않는다. PC 창·전원·인터넷을 유지하며 운영자는 절전 방지를 직접 확인한다. quit/창 닫기는 전체 운영 종료다.0개 선택은 모델의 양성 예측이 없다는 뜻으로 현재 문제에서는 오답이고 같은 라운드를 자동 재추론하지 않는다. busy는 지속 연결이 정상 유지되고 있다는 뜻일 수 있으므로 다음 참가자마다 새 코드를 넣지 않는다. 연결 유실·방 만료·잘못된 최초 연결처럼 세션을 유지할 수 없는 경우에만 새 방으로 복구하며 다른 진행 레인은 건드리지 않는다.

앞선 단일 라운드 PC 실행의 CUDA3모델 로드7.297초는 `runs/remote-engine/20261027-085448-1262f33b/startup.json`에 코드 자동 입력/경기 시작0회로 확인됐다. 이는 당시 기록이며 지속 세션 게시·PC 재시작·현재 가동은 STATUS가 정본이다. 모델 로드 완료와 방 참가/ready 성공을 구분하며 초기 코드로 engine과 viewer가 연결되고 생존 조건까지 충족해야 해당 방이 준비된다.

원격 `remote`는 `mode`, `lane`, `viewerConnected`, `engineConnected`, `engineHeartbeatReceived`, `gpuReservationSupported`, `engineStage`, `sequence`, `lastSelectionAt`과 봇/엔진용 `selectedIndices`를 제공한다. 인간 응답에는 선택 번호를 넣지 않으며 봇의 번호도 정답이 아닌 행동 표시다. viewerConnected는 참가 기록이고 지속 생존/사진 로딩 보증은 아니다. ready·15초 생존·viewer 참가가 준비 조건이며 새 queue에는 protocol3 사진 준비 지원도 필요하다. gpuReservationSupported는 이 프로토콜 보고 여부이지 물리 GPU 예약의 서버 측 증명이 아니다.

`engineHeartbeatReceived=false`는 아직 유효한 heartbeat 시각이 없다는 뜻이다. stage=waiting/disconnected는 연결 대기이고 stage=connected에서 이 값이false이면 최초 생존 확인 중이다. 어느 쪽도 ready를 허용하지 않는다. 수신 이력이true인 상태에서 `engineConnected=false`이면15초 만료 등 생존 검증 실패로 표시한다. 이 boolean은 raw heartbeat 시각·토큰·정답 정보를 공개하지 않는다.

서버는 D1 remote 행 읽기를 완료한 뒤 시각을 얻고 같은 시각으로 `serverNow`·engineConnected·bot.ready를 계산한다. 이전에는 읽기 전에 잡은 now와 읽는 중 커밋된 새 heartbeat를 비교해 seen>now가 되면서 살아 있는 엔진이 잠깐 끊김으로 판정될 수 있었다. 제어된 비동기 회귀로 이를 재현해 고쳤다. 진짜 미래 시각의 거부와15초 생존 경계는 그대로이며 유예 시간을 늘리거나 실제 끊김 표시를 숨기지 않는다.

### 계획 ACK·서버 재생·검증 기록

계획의 최소 ACK는 `{plan:{roundId,selectedIndices,startAt,intervalMs:250,submitAt},serverNow}`다. 시작은 수락500ms 뒤, 제출은 시작+`max(0,n-1)*250ms`로 서버가 정한다. 따라서9개 최대2.5초(500ms 전달 여유+2초 타일 재생)이고0개도500ms 뒤 그대로 한 번 제출한다. 예정된 선택 수는 모델 출력 수이며 서버 정답 수가 아니다. 같은 계획의 응답 유실 재시도는 원래 시각을 유지하며 첫500ms를 다시 시작하지 않는다.

round nullable4열 `bot_plan_indices_json/start_at/submit_at/correct`는 `0003_colorful_cassandra_nova.sql`로 추가한다. 기존0000~0002와 방/토큰/과거 결과는 보존한다. `correct`는 서버 전용이며 미래 정답 여부를 ACK나 일반 상태로 제공하지 않는다. 계획 수락 뒤 PC가 끊겨도 맡긴 일정은 서버가 처리한다. 인간이 먼저 완벽 정답을 제출하면 남은 선택을 종료 시각에서 자르고 마감 뒤 새 정답을 만들지 않는다. 인간 제출과 만기 계획 정산은 D1에서 원자적으로 경합해 한 승자를 유지한다. 봇/엔진에게만 예정 번호를 제공하며 인간 응답에는 선택 번호나 계획을 넣지 않는다.

계획 완료 뒤 오답도 서버의 봇 제출 시각/false 결과를 기록하되 인간은 계속 같은 문제를 수정할 수 있다. 이는 기존 개별 오답의 `submitted=false` 호환 표시와 구분한다. 지원 필드가 없는 서버에서만 기존 개별 선택/ACK·submit을 사용한다. 사진은 최대3개 병렬로 다운로드하고9개 원순서를 유지하며 한 장 실패 시 시작한 작업을 정리하고 추론을 중단한다. 사진 경로/바이트/픽셀 제한과 RGB만 모델에 전달하는 경계는 유지한다.

보고서의 `selection_transport=scheduled_plan`, `planned_selection_events`, `planned_submit_at_ms`는 서버 예정 시각이다. 실제 개별 전송을 뜻하는 `selection_events`는 빈 배열, 별도 submit HTTP가 없어 `submit_sent=false`다. `logical_submission_count=1`과 `server_submission_observed`로 계획 수락과 실제 서버 시도를 나눠 기록한다. 검증기는 예정250ms 간격과 실제 ACK후 전송 간격의 표본 수를 별도로 보고하고 인간 선승 때는 예정 집합의 유효 prefix만 표시됐는지 확인한다. 모델/상태HTTP schema2와 선택 전송 schema3를 혼동하지 않는다. 실제 화면 재생·왕복 개선·CUDA·게시/운영 엔진의 완료 여부는 STATUS가 정본이다.

원격 실행기는 세 모델을 한 번 불러 공유하고 단일 추론 잠금으로 GPU 실행을 직렬화한다. 두 세션의 네트워크/상태는 독립적이지만 동시에 GPU 추론을 시작할 때 뒤 순서에는 대기가 생긴다. 이전 공개v8 보고서 A1의 추론 구간1.547초·대기 구간0.391초, B1의 추론 구간0.844초·대기 구간2.250초는 당시 샘플이다. `gpu_queue_seconds`에는 잠금 대기와 최초 active 상태조회 HTTP 왕복, `inference_seconds`에는 모델 판별과 뒤이은 active 상태조회 HTTP 왕복이 포함된다. 순수 GPU 대기·순수 ML 시간이나 그 차이로 단정하지 않는다. 새 속도 보장·현장 네트워크·장시간 부하·정확도와 구분하며 이번에는 기존 근거만 검토하고 새 추론/측정을 하지 않았다.

이전v8은 startAt 뒤 GPU 잠금을 기다려 그 방 참가자가 상대적으로 유리할 수 있었다. 위 A1/B1은 그때의 상태조회 포함 샘플이며 현재 방식의 속도·순수 GPU 잠금 차이·공정성 보장이나 보정값이 아니다.

후속 승인으로 시작 요청→경기 전 GPU 예약 대기→자원 차례에 세 역할9사진 준비→공통 카운트다운→사람·AI 동시 시작→캐시 RGB 추론 후 GPU 해제를 구현했다. 최소0.25초 선택은 다음 방의 추론과 겹칠 수 있다. 서버는 물리 GPU 잠금을 직접 조회하지 않으며 인증된 PC가 예약을 가진 뒤 begin을 보내는 계약이다. 사전 사진 풀이·타이머 사후 보정·추가 임의 지연은 없고 첫 완벽 정답/90초 가안·같은 방 다음 참가자는 유지한다. 최종 실제 GPU·UI·HTTP·배포와 남은 네트워크/현장 차이는 STATUS의 검증 범위를 따른다.
